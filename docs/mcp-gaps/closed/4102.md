# `interact`'s click on a right-to-left window presses the button named, where a person's click reaches the mirror-image one — **CLOSED, won't do** (#4102, 2026-11-17)

**Symptom.** Measured 2026-11-16 on Windows at 150%, on #3973's first lane round (`9c204b0a6`). That round gives a program's
`MsgBox` with `vbMsgBoxRtlReading` the `WS_EX_LAYOUTRTL` style.

```
interact {"target":"Window/Custom/Button[Cancel]","action":"click","window":"Title 1"}
→ "mechanism":"pointer", "clicked the left button at (37.7, 13.3) on 'Button', which is (49.7, 73.3) in the window"
→ the program logged MsgBox's return value: 2 (Cancel)
```

A person's click at the same place on the screen gets **6 (Yes)**. Windows reports a mirrored window's client x from its right
edge, and Avalonia reads a mouse message's `lParam` as it comes, while it draws its content from the left. `interact` injects
into Avalonia's input after that point, so it never meets the mirroring, and it reports a box that works. The person's click was
reproduced without moving the cursor:
- the screen point went through `ScreenToClient`, which gave client (324, 110) of 399 for a point 75 from the left;
- `WM_LBUTTONDOWN` and `WM_LBUTTONUP` were then posted to the window with those coordinates.

Filed as [#4102](https://github.com/hexide-io/HexIDE/issues/4102).

**Workaround.** For a window with `WS_EX_LAYOUTRTL` (read `GWL_EXSTYLE`), check a click the way Windows delivers one:
`ScreenToClient` on the screen point, then post the button messages. Treat `interact`'s answer there as showing only that
the control works.

**Suggested fix.** On Windows, when the target's window has `WS_EX_LAYOUTRTL`, have `click` deliver through the window's own
message path. Failing that, add a note to the reply that the window is mirrored and the click went past Windows' mirroring.

**First step (2026-11-16, with #4103).** `click` now says so when the window is mirrored: "this window is mirrored
(WS_EX_LAYOUTRTL), and the press was raised at the layout point, past Windows' mirroring: a real mouse here arrives with its
client x measured from the right edge, so it reaches the same control only if the window un-mirrors its input". Checked live
on #3973's `9c204b0a6` box, and absent from a click on the IDE's Project Explorer. The press itself is unchanged, so this
entry stays open until `click` delivers through the window's own message path on a mirrored window.

**Closed as won't do, not fixed (2026-11-17).** The click is still raised at the layout point, past Windows' mirroring, with
the first step's note in its reply. Delivering it through the window's own messages was not built, by the supervisor's
decision on hexide-mcp's recommendation, because:
- **It would be a second click implementation.** `ScreenToClient` plus `WM_*BUTTON*` messages arrive as Avalonia's real Win32
  mouse device, not the device automation drives. `click`'s capture, held drags, deferred release and second press all
  follow automation's own device, and Avalonia would take real OS mouse capture as well. All of that, for one kind of window.
- **The risk it would cover is covered already.** The only mirrored windows are a program's `MsgBox` with
  `vbMsgBoxRtlReading` (#3973). Its un-mirroring is the message box's `MouseHookCallback`, which `MessageBoxLayoutTests`
  drives directly: it gives the hook a mirrored `lParam` on a 399-pixel client and checks the point that comes out. The reply's
  note keeps a caller from taking an automation click for a person's.

**What would reopen it:**
- a second kind of mirrored window, whose un-mirroring has no direct test;
- or a case the hook's test can't reach, where a person's click and automation's would part.
