# A border given a name but no type is folded away, name and all, so `match` cannot find it — **CLOSED** (#4046, 2026-11-16)

**Symptom (2026-10-22, #157, headless).** The designer's box for a control HexIDE does not model was a
`ClassicBorderDecorator` with `AutomationProperties.Name` set to the control's name. `dump_visual_tree`'s `match`
path, `UiAutomationDriver.Find(UiAutomationDriver.Dump(window, "Window", 60, interactiveOnly: false), "imlIcons", 10)`,
the code `{"match":"imlIcons"}` runs, found nothing. A border's control type is `None`, it has no provider and takes no
focus, so the control view hides it as plumbing, and the name it was given goes with it. This is the rule
[#1436](https://github.com/hexide-io/HexIDE/issues/1436) is about, reached from the other side: a name set on purpose is
no more plumbing than an AutomationId.

**Workaround.** Give the element a type: `AutomationProperties.ControlTypeOverride="Pane"` keeps it, as `VBProps` does
for a running form's Frame, PictureBox, Label and Image.

**Suggested fix (at discovery).** Count an explicitly set `AutomationProperties.Name` as the AutomationId already counts, so a view's
author is not left to discover the override. The path-stability part of #1436 is fixed; this explicit-name
discovery gap was still open then.

**Fix (#4046).** The control-view rule now keeps a typeless element whose own automation Name is set and
not empty: a local value from markup or code, or a Template value, which is how markup inside a DataTemplate
arrives. That is the same standing an explicit AutomationId already has. A name set by a style or theme, and a
peer name derived only from content, leave a wrapper folded away. The existing `interactiveOnly` filter still
applies to tree dumps; `match` already searches every node.

**Why not every set Name.** The lane's first rule kept any element where `IsSet(NameProperty)` held. Dock's
theme binds `AutomationProperties.Name` to `{Binding Title}` on every `ProportionalDockControl`,
`ToolDockControl` and `DocumentDockControl`, and HexIDE leaves those titles null, so that rule put three nameless
`None` segments into every path under the dock (main window 186 → 189 nodes, measured headlessly by the lane), and
a titled dock would have grown a named one. Avalonia gives style and theme setters `Style` priority
(`StyleTrigger` when a selector activates them), which is what separates them from a view's own name.

**The designer's box no longer needs the rule.** The 10-22 symptom was the designer's box for an unmodelled
control. That box has since been given `AutomationProperties.ControlTypeOverride="Pane"`, the workaround above,
so it is typed and kept whatever this rule says.
