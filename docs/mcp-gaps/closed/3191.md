# `set_file_content` changes a running program's code with no prompt, and its reply doesn't say the run keeps the old code

**Symptom.** Measured on 2026-11-06 at 993091535, with the interpreter's own run and Form1's code window open. While
the project is running or paused, `set_file_content` writes the new code and saves it, raises no reset prompt, and
replies as it does in design mode, for example `{"success":true,"note":"Wrote Form1 to …. Its lines are numbered
1..43 …. Its editor shows the new text; …"}`. The program goes on running the code it started with:

- Running: after `set_file_content {"name":"Form1", …}`, `{"name":"Module1", …}` and `{"name":"Form2", …}` changed
  v1 to v2, `interact {"target":"Window/Button[Command1]","action":"click","window":"Form1"}` still showed
  `form v1 / module v1`. Form2, loaded only after the edit, showed `Form2 load v1`. A click counter proved the click
  ran: `form v3 / module v2 #2` after an edit to v4.
- Paused at `set_breakpoints {"name":"Form1","lines":[39]}`, the `Label1.Caption` line: a `set_file_content` that
  inserted three lines above the procedure left `get_debug_state` at `"line":39`. That is now
  `Private Sub Command1_Click()`, and the editor drew the break there. `continue_program` ran the old code (`#3`).
- A breakpoint set after the edit, `set_breakpoints {"name":"Form1","lines":[42]}`, on the new text's
  `Label1.Caption` line, never fired (`#4`). Line 42 of the running code is `Private Sub Form_DblClick()`.
- `type_text` in its default document mode did the same, `typed 39 char(s) into TextEditor`, with no prompt.
  `"mode":"keyboard"` raised the prompt and said so.
- The next run ran the new code.

rdcore saw the same missing prompt during an external debug session (#2053). The editor's guard opens only when
keyboard or clipboard input arms it (`CodeEditorView.ArmResetPrompt`), and `set_file_content` checks no run state.

**Workaround.** Before editing code with `set_file_content` or `type_text`, call `get_debug_state`. If `running` is
true, `stop_project` first, or treat the edit as applying to the next run only. Don't trust a break line or a
breakpoint set after the edit until the run ends.

**Suggested fix.** Report, rather than refuse or prompt. A change during a run has real uses: rdcore's #595 check needed
one. While the project is running or paused, the reply should say that the run keeps the code it started with, and that
the change takes effect at the next run. It should also say that the break location, while paused, and any breakpoint
keep the running code's line numbers, so they won't match the new text until the next run. Until the run ends,
`get_debug_state` and `set_breakpoints` should name the documents changed since the run started. #3191 has the
measurements; #710 tracks the prompt question for every programmatic edit.

**Resolution.** Fixed in #3191 by reporting, not refusing: no prompt was added, and the keyboard reset prompt is unchanged. While a project is running or paused, `set_file_content` and document-mode `type_text` add a note: the run keeps the code it started with, and the change takes effect at the next run; breakpoints, and while paused the break location, keep the running code's line numbers. The IDE tracks the documents changed since an interpreter or external run started, whether in the model or in an editor's buffer, and `get_debug_state` and `set_breakpoints` name them until the run ends. Headless tests cover both tools running and paused, an edit made outside them, design mode, and the list clearing at `stop_project`.
