# `list_lsp_messages` told a filtered poll that nothing was recorded, when only its filter matched nothing — **CLOSED** (#2974, 2026-11-03)

**Symptom.** Measured by hexide-frm on 2026-11-03, against RDCore's language server. 1,337 envelopes were recorded on
`rdcore-vba` after sequence 600, none of them failures.
`list_lsp_messages {"connectionId":"rdcore-vba","failuresOnly":true,"afterSequence":600}` replied
`"note":"Nothing was recorded, answered or ended after 600. Poll again from latestSequence."` The same call without
`failuresOnly` returned `"matched":1337`.

**Cause.** This is #1313's quiet-poll note, in `CaptureQueries.ExplainEmpty`. It is chosen when the same filter without its
cursor would match something; here `failuresOnly` matched earlier cancellations. Its wording dropped the filter. So a
caller asking "has anything gone wrong since I looked?" got the right answer for the wrong reason, and one asking "is
the server still talking?" got the wrong answer.

**Workaround.** Poll once more without the narrowing filter, keeping `connectionId` and `afterSequence`.

**Fixed.** When envelopes did arrive after the cursor, the note now says that nothing matching the filter came, and how
many envelopes did, for example "Nothing matching this filter was recorded, answered or ended after 600, though 1337
envelope(s) were. Poll again from latestSequence with the same filter." A poll that is quiet without its filter still
gets #1313's wording. `CaptureQueriesTests.A_poll_quiet_only_for_its_filter_says_what_did_arrive_rather_than_that_nothing_was_recorded`
fails on the old wording. The 1,337 above is the issue's count, not a rerun: this fix was not checked live.
