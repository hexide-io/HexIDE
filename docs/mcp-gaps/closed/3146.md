# Escape's reply names the watch row's border instead of its menu — **CLOSED** (#3146, 2026-11-05)

**Symptom.** Measured on Windows Server 2025 with builds 201c51770 and e8408a5eb in
[#3146](https://github.com/hexide-io/HexIDE/issues/3146): after `add_watch {"expression":"1 + 1"}`,
`interact {"target":"…/TitleBar[Watches]/Pane[Watches]/Custom/Tree/ScrollViewer/TreeItem[1 + 1]","action":"click","value":"right","window":"ide"}`
opened the tree's context menu. Then
`press_key {"target":"…/TitleBar[Watches]/Pane[Watches]/Custom/Tree/ScrollViewer/TreeItem[1 + 1]","key":"Escape","window":"ide"}`
closed it but replied `pressed Escape on ContextMenu, at …/TreeItem[1 + 1]/None[SelectionBorder]`.
The receiver was at `…/Tree/ContextMenu`; feeding the reply's path back addressed the row's border.

**Workaround.** Discover the open menu with `dump_visual_tree` and address it directly.

**Suggested fix / resolution.** `PathWithin` returns null when its walk stalls at a node that is not a visual ancestor of the target.
A folded target still gets its nearest addressable ancestor's path, preserving editor receiver addresses
and inherited pointer sources.
Receiver addresses fall back to the window's control view when the addressed subtree does not contain the receiver. All callers accept a missing path.
Headless regressions use the Watches view's context menu placed on its row's selection border and
check both the null subtree path and Escape's menu address. Restored hover and inherited-pointer
expectations both fail with the unconditional-null implementation and cover folded visual descendants.

supervisor's running IDE: repeat the calls above, confirm the reply names `…/Tree/ContextMenu`,
contains no focus-move note, and the menu disappears from both the tree dump and the screen.

For current calls, use `TitleBar[Watches]` → `TitleBar[Tool.watches]`, `Pane[Watches]` → `Pane[Tool.watches]`. The calls above retain their historical measurement.
