# `move_control` on a Line says it moved the Line, but its X1 to Y2 don't change — **CLOSED** (#5784, 2026-11-27)

**Symptom.** Measured 2026-11-27 on a Debug build of main `ac5bf463c`, with a project opened from disk whose twips form
holds one Line, `Line1`, from X1 600, Y1 600 to X2 2400, Y2 1200. The Line isn't in the toolbox yet (#163).
- `view_designer(name: "Form1")`, then `get_form_controls(formName: "Form1", controlName: "Line1")`. The control row
  read `"left":0,"top":0,"width":0,"height":0`, though the endpoints cover 40 to 160 pixels across and 40 to 80 down.
- `move_control(formName: "Form1", controlName: "Line1", left: 50, top: 40)` replied
  `{"success":true,"note":"Line1 is at Left 50, Top 40, Width 0, Height 0, in pixels relative to its container, as get_form_controls reports them."}`.
- The same `get_form_controls` call then read `"left":50,"top":40`, while X1 to Y2 still read 600, 2400, 600 and
  1200. `get_undo_state()` gave `canUndo: false`, `get_document_tabs()` gave the form `isModified: false`, and
  `take_snapshot(window: "ide")` showed the Line where its endpoints put it.

`move_control` writes `left` and `top` to the model's Left and Top (`IDE/HexIDE.Desktop/Server/HexIdeTools.cs:1840-1843`),
which a Line doesn't have in VB6, and reports them back (`:1847-1853`). The designer moves a Line by its endpoints,
through `ComponentInstanceViewModel`'s `Left` and `Top`, which `move_control` doesn't use. A save doesn't write the
stray Left and Top (run through `FormSerializer` on `ac5bf463c`), so the file isn't harmed. Only the replies are wrong.

**Workaround.** Move a Line with `set_control_property` on `X1`, `Y1`, `X2` and `Y2`, in the container's units, which
`get_form_controls` lists as settable (not run here), and read its place from those four property rows rather than
from the control row.

**Suggested fix.** For a Line, `move_control` either refuses, naming X1 to Y2 and `set_control_property`, or moves
both endpoints through the designer's own Line move and reports X1 to Y2 as read back, including a move the designer
refuses (#5759). It refuses `width` and `height`, which a Line doesn't have. `get_form_controls` gives a Line's control
row the rectangle the designer selects it by, or leaves the four fields out and says why. Tracked by #5784.

**Fixed** (#5794, batch 502, `fe7de8958`). The refusal was chosen over a move through the designer, which in a scale
HexIDE can't convert writes a twips delta (#5759).
- **`move_control` refuses a Line before any drag starts,** whatever arguments it gets. Nothing changes: no property,
  undo step or modified mark. The error gives the Line's X1, Y1, X2 and Y2 in its container's scale, as the property
  rows show them, and names `set_control_property` for them.
- **`get_form_controls` keeps a Line's four bounds at 0,** so the reply's shape is unchanged. The row's note says why
  and that `controlName` gives the endpoints, beside the undrawn-component note where both apply.

`DesignerLineMoveTests` and `FormControlsSummaryTests.Line_summary_explains_its_zero_bounds` cover both, through the
same `HexIdeTools` methods the tools call. Not live-checked, since only the tools' replies changed. Moving a Line
through `move_control`, rather than setting its endpoints, can follow once #5759 is settled.
