# No way to check a layout at 100% on a display scaled to 150% — **CLOSED** (#3083, 2026-11-04)

**Symptom.** Measured on 2026-11-04 by the rdcore session during #3078's live check, on Windows Server 2025 with the
display at 150%. A check at 100% needs the IDE to run at scale 1, and nothing in HexIDE or its MCP tools sets that.
`AVALONIA_GLOBAL_SCALE_FACTOR=1` in the launch environment is ignored on Windows with Avalonia 12.0.5. With it set,
the IDE was launched through `scripts/dev-ide.ps1`. Then `set_window_state {"state":"Normal","width":860,"height":640,"x":0,"y":0}`
still answered `"scale": 1.5`, and `take_snapshot {"window":"ide"}` was 1290 × 960. `set_window_state` reports the
scale but takes no argument to change it.

**Workaround, before the fix.** Mark the build's executable DPI-unaware for your user only. Add a string value
`~ DPIUNAWARE`, named with the exe's full path, under `HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers`.
Windows then reports 96 DPI to that exe, `set_window_state` answers `"scale": 1`, and Windows stretches the window to
the screen. Remove the value afterwards.

**Why the flag gives scale 1 and nothing else.** An arbitrary scale, such as 2 on a display at 100%, would catch more
of the bugs these checks exist for. Avalonia 12.0.5 has no route to one on Windows. `Win32PlatformOptions` has no scale
property, only `DpiAwareness`, whose values are unaware, system-aware and per-monitor-aware. And
`AVALONIA_GLOBAL_SCALE_FACTOR`, with the other scale variables, is in `Avalonia.X11.dll` alone. Both were read from the
package's own XML docs and assembly strings. Unaware is the only mode that moves the scale, and only to 1.

**Fix (#3083).** A Debug-only `--dpi-unaware` launch flag sets `Win32PlatformOptions.DpiAwareness` to `Unaware`.
Off Windows the flag stops HexIDE starting, with exit code 2. With the flag on, `get_window_state` carries a note
saying why the scale is 1. DWM's frame bounds are physical pixels whatever the caller's awareness, so `frame` used to
come out the display's scaling larger than `outer`. It is now converted into the window's own coordinates, as `outer`
and `client` are.

**Live check (Windows Server 2025, display at 150%, 2026-11-04).** Both runs used the same build and
`set_window_state {"state":"Normal","width":860,"height":640,"x":0,"y":0,"window":"ide"}`.

| | No flag | `--dpi-unaware` |
|---|---|---|
| `scale` | 1.5 | 1 |
| `take_snapshot {"window":"ide"}` | 1290 × 960 | 860 × 640 |
| `take_snapshot {"window":"ide","includeFrame":true}` | 1294 × 1007 | 862 × 672, title bar included |
| `outer` / `frame` | 874.7 × 677.3 / 862.7 × 671.3 at (6, 0), as before the fix | 876 × 679 / 862 × 672 at (7, 0); before the fix 1292 × 1008 at (11, 0) |
| Window's DPI and awareness, read from outside | 144, per-monitor | 96, unaware |
| On the screen | 1312 × 1016 | 1314 × 1019, stretched by Windows |

The snapshot's text is sharp, because Avalonia draws it at scale 1 as a 100% display would. The screen shows the same
window bitmap-stretched, with blurred text. So judge glyphs from `take_snapshot`, not from a capture of the screen.
