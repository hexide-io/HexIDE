# A hover didn't stay, so what is drawn only under the pointer couldn't be snapshotted — **CLOSED** (#2562, 2026-10-28)

**Symptom (2026-10-28, Windows at 150%, hexide-frm, #2490's live check).** A running form held a flat Toolbar whose
HotImageList draws a different image while the pointer is over a button. The calls were:
- `interact(target: "Window/Custom[Toolbar2]/Button[#0]", action: "click", window: "Form1")`;
- then `take_snapshot()`, which showed the normal image and no hot border;
- the same with `Button[#3]`, plus a one-second wait.

No call left the pointer over a control. `hover` moves it through the window's input, but ends by taking it out of the
window (#2407), so its tip closes and nothing stays pointer-over.

**What the issue first guessed, and what was measured.** The issue guessed that something cleared the pointer-over
state after the click, perhaps the real mouse. It was never set. `click` raises its press and release on the control,
not through the input manager, and only the input manager sets `IsPointerOver`. Measured on the running form with a
CommandButton: `inspect_element` gave `isPointerOver: false` straight after `interact click`, with no other call
between them, and again after a `take_snapshot`.

**Workaround, before the fix.** None for a snapshot. A tip's text, and a program's MouseMove, could be checked
through `hover`'s reply.

**Fixed (#2562).**
- **`hover` takes `stay`.** The pointer is left on the point when the watch ends, so what it landed on keeps its
  pointer-over look, and an opened tip stays open.
- **The reply says how that settled.** It reads the state 200 ms later, with the foreign-pointer watch still
  running: either the control reads as under the pointer, or the reply names what took it.
- **The next click, drag or hover in that window ends it first**, as a hover's end would have. Without that, a click
  elsewhere left the first control hot, with its tip over the second.
- **An open tip is one of its owner's popups**, so `take_snapshot` draws it with the window, and `dump_visual_tree`
  lists its text under its owner. The snapshot used to draw menus, flyouts and the code window's popups, but never a
  tip.
- **`inspect_element` reports `isPointerOver`.**
- **Guarded by `HoverStayTests`.** Without the click's end of a staying hover, or without the tip's popup, a test
  fails.

**Live (2026-10-28, Windows, headless `claude -p` from the descriptions alone, asked only for a screenshot of a toolbar
button's hover look).** With the real cursor parked on the taskbar:
- **The caller found `stay` from the descriptions.** `hover(…/Button[Standard.SaveProject], stay: true)` replied
  `tip: Save Project …; the pointer stays there and 'Button[Standard.SaveProject]' reads as under it
  (isPointerOver)`.
- **`inspect_element` agreed:** `isPointerOver: true`.
- **A click in the Project Explorer ended it:** `isPointerOver: false`.
- **The snapshot draws the tip.** A second run, after tips joined their owners' popups, hovered
  `…/Button[Standard.ObjectBrowser]` with `stay: true`. `take_snapshot(window: "ide")` showed the "Object Browser" tip
  drawn below the button.

**What remains.** A real mouse resting over the window takes the stay back at once. Windows sends a move at the
cursor's resting point whenever a window appears under it, a tip's popup among them. With the cursor over the IDE,
three hovers out of three were taken back, each to the same point, and the reply named it. No tool moves the real
cursor, so this is filed as #2666.
