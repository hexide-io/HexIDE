# On native Wayland, `hover`'s first tooltip of a session reported `tipBounds` at 0,-30, read before the compositor placed it — **CLOSED** (#4627, 2026-11-18)

**Symptom.** Measured 2026-11-18 with `--platform wayland` under GNOME on openSUSE Leap 16, at #3603's build, Avalonia 12.1.6.
The IDE was maximised at 1024x768, and its window coordinates sat at (+2, +59) on the console. The session's first tooltip:

```
hover {"target":"Window/Custom[MainView]/None[#0]/None[StandardToolbar]/Button[Standard.SaveProject]","window":"ide"}
→ "tip: Save Project (its top-left 107 left of and 65 above the point hovered); seen open about 441ms after the move"
  "tipBounds":[0,-30,77,21]
```

The next seven calls matched the console within 2 px: Save Project `[107,25,77,21]` and Open Project `[85,25,79,21]`,
alternating with the tip closed in between. So 1 of 8 reads was wrong, and the reply gave no sign of it.

**Cause, reasoned and not traced.** (0, -30) is a popup at 0,0 less the 30 px from the window's surface top to its client
area. So the popup's position hadn't come from the compositor, in `xdg_popup.configure`, when `hover` read it on first seeing
the tip open (`UiAutomationDriver.OpenTipBounds`).

**Workaround.** Hover the same control again: the second read comes after the popup is placed. A `tipBounds` at or above
the window's top edge, far from the point hovered, is the tell.

**Suggested fix.** On native Wayland, read a popup's place only once the compositor has configured it: wait, bounded, for
its first position change. Or leave `tipBounds` out with a note while it hasn't arrived. Check whether `inspect_element` and
`take_snapshot` straight after a popup opens can hit the same race; a menu read at once after `interact expand` was right.
Filed as [#4627](https://github.com/hexide-io/HexIDE/issues/4627).

**Fixed.** Native Wayland popup coordinates are read only after the platform reports a non-default position.
`hover` waits up to 500 ms for the tip's first position change; if it remains unplaced, the reply omits `tipBounds`
and explains that hovering again reads its position. `inspect_element` omits `boundingRect`, and `take_snapshot`
leaves the unplaced popup out, each explaining why and asking the caller to retry. Headless integration tests cover
placement arriving through the dispatcher and the timeout, plus synchronous reads at 100% and 150% scaling.
**Live check** (hexide-mcp, 2026-11-18). The review build `ed977a86a` was published linux-x64 Debug and run with
`--platform wayland` under GNOME on openSUSE Leap 16, Avalonia 12.1.6. There were eight fresh launches, each with a new
`--user-data-dir`, and each session's first `hover` was on a Standard toolbar button.
- **Every reply carried `tipBounds`,** with no placement note: Start `[282,25,36,21]` three times, Open Project
  `[85,25,79,21]`, Toolbox `[443,25,53,21]`, Add Form `[34,25,63,21]`, Save Project `[107,25,77,21]` and Object Browser
  `[421,25,92,21]`. The tips were seen open 450 to 497 ms after the move.
- **The second run's tip,** kept open with `stay`, sat at window (282, 25) on the Hyper-V console capture.
- **The unplaced path didn't occur live.** It came up in 1 read of 8 before the fix, so the wait and the note are
  covered by the headless tests only.

**Known limit, reasoned and not checked.** A popup the compositor places exactly at its parent surface's origin keeps
the default position, so it would read as unplaced every time. Under client-side decorations that origin is in the
window's shadow, where no tooltip or menu here opens.
