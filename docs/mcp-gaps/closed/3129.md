# Escape sent to a tree node leaves its context flyout open — **CLOSED** (#3129, 2026-11-05)

**Symptom.** Measured on Windows Server 2025 with build 201c51770, as recorded in
[#3129](https://github.com/hexide-io/HexIDE/issues/3129):
`interact {"target":"…/Pane[Project Group - Group1]/Custom/Tree/ScrollViewer/TreeItem[Project1 (Project1.vbp)]/TreeItem[Form1 (Form1.frm)]","action":"click","value":"right","window":"ide"}`
opened the TreeView's ContextFlyout. Then
`press_key {"target":"…/Pane[Project Group - Group1]/Custom/Tree/ScrollViewer/TreeItem[Project1 (Project1.vbp)]/TreeItem[Form1 (Form1.frm)]","key":"Escape","window":"ide"}`
moved focus from the menu to the node and left the flyout open.

**Workaround.** Address the focused menu item from `dump_visual_tree` and send Escape there.

**Suggested fix / resolution.** For unmodified Escape, `press_key` now retains focus in an open
attached menu or flyout whose placement target contains the addressed control. Other keys retain
their existing routing. The reply names the popup receiver using its window-rooted path.
A headless regression opens a TreeView ContextFlyout, addresses its node by the saved path, and
checks that Escape closes the flyout without moving focus first. Live verification is pending the
supervisor's running IDE: repeat the calls above and confirm that the reply names the menu item,
contains no focus-move note, and the flyout disappears from the dump and the screen.

For current calls, use `Pane[Project Group - Group1]` → `Pane[Tool.project]`. The calls above retain their historical measurement.
