# A new document opens in the first area and its opening reply omits the area — **CLOSED** (#3795, 2026-11-12)

Symptom: measured on Windows at 150% on #3784's fix (9ca2aaacd plus its review edit), as recorded in
[#3795](https://github.com/hexide-io/HexIDE/issues/3795). With Module2 moved into a second document area,
these calls opened Form1's new code tab in area 0:

```text
activate_document_tab {"title":"Probe3784 - Module2 (Code)"}
open_file {"name":"Form1"}
get_document_tabs {}
```

The last reply reported Form1 active in area 0 and Module2 inactive in area 1. The opening reply gave
focus and caret information without the area. An already open Form1 code tab in area 1 stayed there
with `open_file {"name":"Form1","line":21,"column":25}`.

Workaround: ask `get_document_tabs {}` after opening and rediscover the editor path in
`dump_visual_tree {}` before typing; a previously captured path can still identify the other document.

Fix: new editors use the document area that last held focus, falling back to the first.
`open_file` and `view_designer` return `area`, numbered from 0 in layout order.
Headless tests cover opening in the second area, retaining it after tool focus, the unsplit fallback,
existing-tab activation, and the reply field. Live verification is pending supervisor review: repeat
the calls above and check that Form1 opens in area 1, then check the designer reply and visible area.
