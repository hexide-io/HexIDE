# A `window` name a dialog shares with its own message box is refused with advice no caller can follow — **CLOSED** (#2712, 2026-10-28)

**Symptom.** Found by a first-contact headless run on 2026-10-28. It drove Edit → Find, searched for text that wasn't
in scope, and Find Next raised a message box over the dialog. The box is titled "Find" too. Then:

```
dump_visual_tree {"window":"Find"}
→ 2 open windows answer to 'Find', as two instances of one form do: "Find", "Find". Name one by a title only it has.
```

No title names either one alone, and a dialog with its message box isn't two instances of one form.

**Workaround.** Omit `window`. `auto` prefers a dialog, so a bare dump reached the message box, but nothing in the
refusal said so.

**Fixed.**
- **Stacked windows:** where the windows sharing a name sit on one another, each owning the next, the name reaches the
  one on top, as `auto` would. That is the only one a person can use, and the name reaches the dialog again once the
  box closes.
- **A failing path:** a path that then fails, such as one from a dump of the dialog taken before the box opened, says
  that the name reached the window on top of another of that name.
- **Side by side:** for windows of one name side by side, as two instances of one form are, the refusal now says
  which one `auto` reaches, rather than to name one by a title only it has.
- **Tests:** `ForegroundWindowTests` covers all three cases.
