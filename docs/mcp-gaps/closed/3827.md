# Code-window clicks reported pixels without the line they reached — **CLOSED** (#3827, 2026-11-12)

**Symptom.** #3827 records `interact` clicks on a code window's `BreakpointMargin` with
`action: "click", value: "7,76 right"` reaching line 5 before a language server's code lens loaded,
and line 4 afterwards. The issue does not retain the complete target path. At 150% on Windows,
main at 4d8d35fec, line 5's dot moved from y 76 to y 89. The reply reported only pixels, so the caller
mistook the code window's correct context menu for a breakpoint-menu defect. Measurements and the
corrected diagnosis are recorded in [#3827](https://github.com/hexide-io/HexIDE/issues/3827).

**Workaround.** Take another snapshot after lenses load and recalculate the point.

**Fix.** `click`, `double_click` and drag replies now identify the document and rendered line, the column
in text, and breakpoint/bookmark marks present when pressed. `interact(target: "Window/#BreakpointMargin",
action: "click", value: "line:5 right", window: "ide")` aims at the line's glyph after scrolling it into
view. Text also accepts `line:5,col:3`. A line beyond the document is refused with its line count.
Pixel coordinates remain accepted. Headless tests cover text and the breakpoint, line-number and fold
margins at 150%; the supervising session still needs to verify the running IDE with a delayed code lens.
