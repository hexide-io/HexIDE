# A floating window could not be made inactive — **CLOSED** (#4223, 2026-11-16)

**Symptom:** While live-checking #4154 on Windows, a floating tool's inactive title bar could not be checked.
`activate_document_tab(name: "Form1", type: "designer")` moved Dock's active document and keyboard focus,
but left the floating window OS-active. The call
`interact(target: "Window/Custom[MainView]/…/None[FormContainer]", action: "click", value: "100,100", window: "ide")`
pressed and released in the IDE without activating it, although the reply sounded like a person's click.
`set_window_state` accepted only Maximized, Normal or Minimized.

**Workaround:** Relaunch with a saved layout that restores the floating window inactive. A headless test
can deliver Avalonia's `HandleDeactivated` callback, as `ToolFloatingTests` does.

**Fix:** `set_window_state(window: "ide", activate: true)` now requests platform activation and waits up to
one second for confirmation. `state` is optional; passing neither a state nor activation is refused with
instructions. Activation is permitted only while a HexIDE window is already active; on Windows the
foreground HWND must also belong to this process. A blocking modal dialog is named and must be answered
first. The reply gives the target's `isActive` and `previouslyActive` name and `isActive`; a timeout is
reported honestly. A click that starts and ends on an inactive window names the window still active and
points to this explicit activation call. It does not alter the press.

Headless regressions cover the dispatcher-delivered activation and real pointer release. The supervisor's
Windows live check remains to confirm native foreground switching and inactive title-bar rendering;
this entry does not claim that check has run.
