# Failed breakpoint conditions looked true and printed debugger errors — **CLOSED** (#3830, 2026-11-12)

**Symptom.** The Windows probe recorded in [#3830](https://github.com/hexide-io/HexIDE/issues/3830)
called `set_breakpoints {"name":"Main","lines":[7],"conditions":{"7":"x >"}}`, then
`run_project {}`, `get_debug_state {}` and `get_last_runtime_error {}`. The run paused at line 7
with `stopReason: "Breakpoint"`, `printed: "x >: Syntax error\n"`, and no runtime error raised.
A caller could mistake the failed evaluation for a true condition and debugger output for program output.

**Workaround.** Read the Immediate window's error and repair the condition; neither an ordinary
breakpoint reason nor `get_last_runtime_error` explained the stop.

**Fix.** Breakpoint stops now carry the failed expression and evaluation error. Run, continue and step
notes and `get_debug_state.note` explain that the condition could not be evaluated and name its line.
The reason remains `Breakpoint`; its detail distinguishes failure from a true condition. The localized
status bar shows the same failure while paused. Evaluation errors are excluded from the console stream
and therefore from `printed`.

**Verification.** Headless debugger and tool regressions exercise `x >` and a `missingName` local
declared in a different procedure. HexIDE currently rejects both with `Syntax error`. This records
HexIDE behavior, not a VB6 measurement. Both expressions are covered in run and step replies, which
retain real preceding `Debug.Print` output without the debugger error. Seven cases (two debugger, four
tool and one status-bar) fail with main's implementations restored; the additive stop-detail fields are
retained so the tests compile. All seven pass with the fix restored. Live IDE verification remains
with the supervising session: check the paused status bar, then resume and confirm that the failure
message clears.
