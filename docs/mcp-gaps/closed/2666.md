# A real mouse resting over the IDE takes a staying hover back, and no tool can move it

**Symptom (2026-10-28, Windows, the workstation's unattended desktop, #2562's live check).** The real cursor rested at
(697, 565) on screen, over the IDE window. Three times out of three, `hover(target:
"…/Button[Standard.SaveProject]", window: "ide", stay: true)` replied that the button `does not read as under it
(isPointerOver is false): the real mouse moved the pointer to (696.7, 542) in the window … during the watch`, and the
tip was gone. Windows sends a mouse move at the cursor's resting point whenever a window appears or changes under it,
and the tip's own popup is such a window. Avalonia then moves pointer-over to what is under the real cursor.

**Workaround.** Park the real cursor off the IDE's windows before the hover, outside the tools: with the cursor on the
taskbar, the same call held and `inspect_element` gave `isPointerOver: true`. A caller limited to the hexide tools has
none.

**Suggested fix (at discovery).** #2666 listed three options, then undecided:
- while a hover stays, ignore a foreign move at the point of the last one;
- a tool that parks the real cursor;
- leave it, since the reply names the cause.

**Fixed (#2666).** Option A was chosen: the platform input callback is wrapped before Avalonia's pointer-over
preprocessing, on windows and popup roots. Real-device screen positions are recorded even without a stay. From the
staying hover's move, through its tooltip dwell and stay, only moves within 1 screen pixel of that device's previous
position are dropped; a new position or an unknown first position still passes through, with the existing
foreign-pointer reply. No OS cursor is moved. Native Wayland input remains unchanged because its backend does not
supply screen positions
(`NativeWayland` records that limitation); the filter never compares its invented origin.
[Avalonia 12.1.4's presentation source](https://github.com/AvaloniaUI/Avalonia/blob/12.1.4/src/Avalonia.Controls/PresentationSource/PresentationSource.cs)
assigns the input callback in its constructor and clears it on disposal; visibility installs the wrapper before input,
including on popup roots. Debug startup installs tracking before the IDE's windows open.

**Verification.** Headless tests cover the callback before pointer-over and tooltip processing. **live check pending
(hexide-mcp)**: leave a real mouse resting over an IDE window, hover the Save Project button with `stay: true`, then
check `inspect_element` gives `isPointerOver: true` and a snapshot includes its tip. A genuine mouse move must still
take the stay back and keep today's reply. Wait for a resting mouse; do not move the OS cursor with automation.

**Dwell coverage (#2666 round 2).** `HoverAsync` registers the stay in the same dispatcher operation as its move,
before watching for a tip. Cancellation ends that stay. Tool-path headless tests send a real-device move immediately
after a delayed tip opens, before the dwell poll: a known restatement preserves the staying hover, while a new position
and a hover without `stay` keep the existing foreign-pointer reply. The live check above remains pending.
