# Replies around a program's waits leave a held handler's end, an opened form's name and a box's window to be guessed — **CLOSED** (#2720, 2026-10-28)

**Symptom.** Found by the first-contact check of #2567's description cut. It ran headless `claude -p` on WaitProbe, whose Form1 has buttons that show a MsgBox, reach `Stop`, and show Form2 under the caption "Second":
- **Answering the box:** `interact` answered the box with `invoked Button 'OK'`, and with #2657 the printed line too. Neither said cmdBox_Click had finished, so one caller called `get_debug_state` to find out.
- **Continuing from the Stop:** `continue_program` replied `Running; no pause within 2 s`, which says nothing about the handler it resumed.
- **Opening Form2:** the click replied `(the program opened 'Second')`. That is a caption, while `window` calls a form's name the stable handle.
- **Reaching the box:** the click that raised the box named it `'WaitProbe'`, its title, but not that `window: "WaitProbe"` reaches it.

**Workaround.** `get_debug_state`, and trying `window` with names until one worked.

**Fixed.**
- **A finished handler:** `EventPump.FinishedSince` names the walks live before an action that have since ended, a Timer's left out. The reply appends `(cmdBox_Click finished)`, and `continue_program` the same as a sentence.
- **An opened form:** it is named `Form2 ("Second")`, or by its name alone where its caption is the same.
- **A holding window:** a reply that waits on one adds `window "<title>" reaches it`, or `"auto"` where the window has no title.
- **Tests:** `ProgramWaitTests` and `EventPumpTests`.
