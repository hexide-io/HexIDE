# Opening a context menu renumbers its owner's children — **CLOSED** (#3109, 2026-11-05)

**Symptom.** Measured on Windows Server 2025 on 2026-11-04, build 0c456fcce
([#3109](https://github.com/hexide-io/HexIDE/issues/3109)).
`dump_visual_tree {"match":"Form1","window":"ide"}` returned the Project Explorer path
`Window/Custom[MainView]/…/Pane[Project Group - Group1]/Custom/Tree/ScrollViewer/TreeItem[Project1 (Project1.vbp)]/TreeItem[Form1 (Form1.frm)]`.
After `interact {"target":"<that path>","action":"click","value":"right","window":"ide"}`,
`press_key {"target":"<that path>","key":"Escape","window":"ide"}` refused the now-ambiguous
`ScrollViewer` segment. `dump_visual_tree {"root":"…/Custom/Tree","maxDepth":3,"window":"ide"}`
showed the menu's scroller at index 0 and the tree's own scroller moved to index 1.

**Workaround.** Dump the tree again while the menu is open and use its newly indexed paths.

**Suggested fix.** Keep attached popup content below a separate segment under its owner, preserving
all paths into the owner's own subtree.

**Fix.** Attached context menus and flyouts keep a distinct `ContextMenu` or `Flyout` root under
their owner. Dumping and resolving use the same control-view collector. Headless regression tests
check saved paths, unchanged child indexes, and invoking a menu item through the new segment.
Verified live on 2026-11-05 by hexide-mcp (#3128): with the Project Explorer node's menu open, the path
taken before it opened still resolves; menu items are reachable under `ContextMenu` and `Flyout`
segments and `invoke` runs them; the tree's own scroller keeps its index. Escape sent with `press_key` to
the node does not close a menu placed on the tree itself (the TreeView's `ContextFlyout`), because
`press_key` moves focus onto the node first. That is a separate defect, #3129.
