# In a split code window, `open_file` reported the move it had made as a failure — **CLOSED** (#3618, 2026-11-10)

**Symptom (2026-11-10, Windows, found during the live check of #3617).** With a 200-line module open, and `L` the lower pane's editor, `Window/Custom[MainView]/Pane[DockControl]/Pane[Root dock]/List[PART_ItemsControl]/List[#0]/Pane[#0]/Custom[Root]/Custom[Root]/None[TextEditor]`:

```
open_file {name: "Module1", line: 10, column: 1}
invoke_menu_item {path: "Window/Split"}
press_key {target: L, key: "Escape", window: "ide"}
open_file {name: "Module1", line: 120, column: 7}
```

The last reply read "Keyboard focus is in it. The caret is at line 10, column 1: offset 104 in the text get_file_content returns. That is not line 120, column 7, as asked: the editor moved it, so type_text would write there." The lower pane had moved to line 120. Focus had gone to the top pane, whose caret was still at line 10, and the reply read that pane's caret. Nothing in the reply said there were two panes.

**Workaround.** Give the lower pane focus again with `press_key` and read the status bar, or inspect both panes.

**Cause.** Navigation moves the pane that last had focus, the only one that exchanges a caret with the shared view model. Keyboard focus was given to the first text area in the window, by both routes that give it: the main view's for any activation, and `open_file`'s own. Focusing a pane makes it the active one and writes its caret into the view model, so the top pane's old caret replaced the new one before the reply read it back.

**Fix.** `CodeEditorView.ActiveTextArea` names the pane navigation moves, and both routes focus it. An unsplit window has one pane, so it doesn't change. A person going to a line from elsewhere in the IDE goes through the first of those routes, and was left typing in the top pane the same way.

**Live check (Windows, 150%, at this change).** The calls above replied "Keyboard focus is in it. The caret is at line 120, column 7: offset 981". `focusedPath` was the lower pane, a capture showed lines 119 to 121 in it and `Ln 120, Col 7` in the status bar, and `type_text` with `mode: "keyboard"` on `L` wrote at the end of line 120. Switching to another tab and back rebuilds the window's view, with the top pane active and the lower pane back at line 1, as it did before this change; `open_file` then moved the top pane, and the reply, the focus and the status bar all agreed on `Ln 60, Col 3`.
