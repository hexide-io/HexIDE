# Automation can't see or drive the macOS menu bar — **CLOSED** (#5066, 2026-11-20)

**Symptom.** Measured headless on `c5da3001d` by hexide-mcp, 2026-11-20, as recorded in
[#5066's brief](https://github.com/hexide-io/HexIDE/issues/5066#issuecomment-7032025770): an IDE window held an
in-window File menu, the application's NativeMenu held About HexIDE, and an activated Form1 held
File › Open in its NativeMenu. These calls used the tools' other defaults:

| Exact call | Reply / observation |
|---|---|
| `dump_visual_tree(window: "menubar")` | `Unknown window 'menubar'. Use "auto" … or the name or title of an open window: "Form1". …` |
| `dump_visual_tree(window: "Form1", match: "Open")` | 0 matches: `Nothing matches 'Open'. …` |
| `inspect_element("MenuItem[File]", window: "menubar")` | The same Unknown window refusal. |
| `interact("MenuItem[File]/MenuItem[Open]", "invoke", window: "menubar")` | Refused on the window before reading the path; Open's Click raised 0 times. |
| `invoke_menu_item("HexIDE/About HexIDE")` | `No item 'HexIDE' in the menu bar. It holds: File` |

**Workaround.** None through the window's control tree: native menu objects are outside it.

**Suggested fix.** Expose Avalonia's NativeMenu model separately, using the same item addressing and
state fields as window controls, and choose native items through Avalonia's exporter events.

**Fixed.** #5066 adds `NativeMenuBar` and routes `window: "menubar"` to it in the generic trio. Paths
start at `MenuBar`, for example `MenuBar/MenuItem[File]/MenuItem[Open]`. The app menu comes first,
then the single visible active window's native items, falling back to `auto` when zero or several windows
read active. Replies name that window and selection rule. The tree reports enabled, hidden and checked
state; opening raises NeedsUpdate then Opening, choosing a leaf raises Click once, and collapse raises
Closed. Disabled and hidden items are refused; a submenu, including an empty one, takes expand rather
than invoke. Separators have no actions. Snapshot and window input tools explain why this scope is
unavailable and name the tools that reach it. `invoke_menu_item` accepts the app menu title; the IDE's
in-window route is preserved.

`MenuBarToolTests` exercises the actual tool entry points headlessly: tree order, inspection, event
order, app-menu invocation, refusals, checked state, separators, empty submenus, no-menu windows,
empty-bar guidance, unsupported tools and scope/path mismatches. A regression guard confirms native
items remain outside Form1's window tree. Parent-menu opening and collapse follow the tool
mapping specified in the issue; they are not new AppKit measurements.

**Checked on a real Mac** (hexide-mcp, 2026-11-20, Kronos, macOS 27.2.1, with #5065's PR #5088 merged in). A running
form had File (an item ticked, one disabled, a separator, one hidden), an empty top-level menu and Help. AppKit's own
menus were read and chosen through System Events, and each row ran once on the final build:

- The dump's order, items, ticks and disabled state matched AppKit's. The hidden item was absent there and flagged
  `isHidden` here. The app menu's Services, Hide, Hide Others, Show All and Quit are in Avalonia's NativeMenu on macOS,
  so the tools reach them.
- `invoke` on a leaf raised the program's Click for its menu, then for the item, once each, as AppKit's own choice of
  the same item did. `expand` on the empty menu raised its Click once. Disabled and hidden items were refused, and
  nothing ran.
- The reply read Wrap's tick after the program's Click handler had changed it, and AppKit agreed.
- With a modal About box up, AppKit and the dump both showed only the app menu (#5011's K10).
- Not listed: after a real open, AppKit adds an item to Help that holds a text field and a table, most likely macOS's
  Help search field. It isn't in the NativeMenu.
