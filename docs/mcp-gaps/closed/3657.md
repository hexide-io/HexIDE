# Typing replies precede on-type formatting edits — **CLOSED** (#3657, 2026-11-12)

**Symptom.** Measured by hexide-mcp on Windows at 150%, main `abca0d359`, recorded in
[#3657](https://github.com/hexide-io/HexIDE/issues/3657): a scripted stdio server claimed `.bas` files and
advertised `\n` as its on-type trigger. It indented the new line two more columns and inserted `End If`.
After `open_file(name: "Module1", line: 9, column: 17)`,
`type_text(target: <code window TextEditor path>, text: "\n", mode: "keyboard", window: "ide")`
reported offset 147; after the 227 ms answer the caret was 149 (line 10, column 7).
The same calls at line 15 reported 221 instead of 223 after 230 ms; at line 5, 95 instead of 97 after
only 1.3 ms. After `open_file(name: "Module1", line: 38, column: 17)`,
`press_key(target: <code window TextEditor path>, key: "Enter", window: "ide")` followed immediately by
`open_file(name: "Module1")` read line 39, column 5, offset 540, before the 233 ms answer moved it to
column 7, offset 542. The issue records the target as the code window's TextEditor, not its literal path.
`list_lsp_messages` showed the requests Answered: the edits worked, but the replies preceded them.

**Workaround.** Wait for the formatting request to settle, then read the text and caret again.

**Fix.** Both tools now await the editor's pending completion, parameter-info and on-type formatting tasks
before reading back, with the existing 2 s automation budget and no fixed delay when nothing is pending.
The formatting task includes applying or discarding its edits; its own 250 ms request budget is unchanged.
A tool budget expiry names the work that may still change the editor. Gated stub-server headless tests
cover both entry points and their budget notes. Live verification is pending the supervising session:
repeat the calls above and compare each reply's caret and an immediate document read with the applied edit.
