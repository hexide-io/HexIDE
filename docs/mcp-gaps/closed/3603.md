# On native Wayland, `take_snapshot` leaves out open popups and `boundingRect` is unavailable inside one — **CLOSED** (#3603, 2026-11-18)

**Symptom.** Measured 2026-11-10 with `--platform wayland` (#868) under GNOME 48 on openSUSE Leap 16, at the build that closed #3575.

```
take_snapshot {"window":"ide","inline":true}        (with the File menu open)
→ "note":"Left out of this image: a Border popup 237 × 402, which can't be placed because native Wayland's compositor places a
   popup itself and Avalonia doesn't pass on where it went. ..."

inspect_element {"target":".../MenuItem[File]/ScrollViewer/MenuItem[Exit]","window":"ide"}
→ no boundingRect, and "boundingRectNote":"The control is in a popup, and native Wayland's compositor places a popup itself and
   Avalonia doesn't pass on where it went, so boundingRect is unavailable."
```

The reply is honest, but a menu can't be seen in a capture, and `hover`'s `tipBounds` is absent for the same reason. With no flag,
through XWayland, both work. Read from Avalonia 12.1.4's source and not run under a debugger: the compositor reports a popup's place
in `xdg_popup.configure`, and `PopupImpl.Sink.OnPopupConfigure` reads only its width and height. Filed as
[#3603](https://github.com/hexide-io/HexIDE/issues/3603).

**Workaround.** `dump_visual_tree` lists a popup's controls, and `interact` presses them correctly. For the pixels, capture the
compositor from outside the guest.

**Suggested fix.** Avalonia would need to pass the configure event's position on. Until it does, the placement requested of the
compositor can be read by reflection from `PopupImpl._lastPositioner`, and a popup drawn there with a note saying the compositor
may have moved it.

**Fixed.** Removed the native-Wayland exclusions from popup snapshot placement, popup `boundingRect` and tooltip
`tipBounds`. They now use the same screen-coordinate conversion as other platforms. This needs Avalonia 12.1.5 or later:
[AvaloniaUI/Avalonia#22291](https://github.com/AvaloniaUI/Avalonia/pull/22291) reports the compositor's popup positions.
HexIDE pins 12.1.6. Window positions remain unavailable on native Wayland. Headless stand-in tests cover the removed branches,
not the real backend.

**Live check** (hexide-mcp, 2026-11-18, this build under `--platform wayland` on GNOME, openSUSE Leap 16, maximised at
1024x768, console pixels read from outside the guest). In every case the window's coordinates sat at (+2, +59) on the console.
- **File menu, opened with the real mouse:** `take_snapshot` drew the popup where the console showed it, from (4, 78) to
  (240, 508). Exit's `boundingRect` `[5,423,231,24]` matched its row on the console.
- **Edit menu, opened with `interact expand`:** the compositor slid it up about 23 px to fit the screen, over the menu
  bar. Select All's `boundingRect` `[38,220,254,24]`, read straight away, matched the slid row. The snapshot drew the popup
  5 px above the window (`windowOffsetY` 5).
- **`hover`'s `tipBounds`:** 7 of 8 reads matched the console within 2 px. The session's first tooltip read `[0,-30,77,21]`,
  apparently before the compositor had placed it. That is [#4627](4627.md), now fixed and live-checked.
