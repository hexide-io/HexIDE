# `type_text`'s default mode left a live TextBox drawing its previous text — **CLOSED** (#2737, 2026-10-28)

**Symptom.** Found in #2717's live check. In the Find dialog,
`type_text {"target":"Window/Custom/Edit[#0]","text":"Form","window":"Find"}` answered `typed 4 char(s) into TextBox`.
- **The app had it:** `inspect_element` read `Form`, and Find Next found it.
- **The box was drawn empty:** in `take_snapshot`, and in an OS `PrintWindow` capture.
- **One write behind:** a second write, `X`, drew `Form`, with the caret after a gap where the `X` should be.

**Workaround.** `mode: "keyboard"`.

**Cause.** Measured with a probe build: the box's `TextPresenter` held the new text and a layout of the right width, but
drew the previous text's glyphs.
- Invalidating its `TextRunCache`, new in Avalonia 12, cleared it, and a fresh render did not.
- The same code is in 12.1.4 and on Avalonia's main. Their #21902 fixed this class of bug for `TextBlock` only.

**Fixed.**
- **The write's order:** `UiAutomationDriver.TypeText` commits a TextBox write in the order `TextBox.HandleTextInput`
  uses. That is `SetCurrentValue(Text)`, `ClearSelection`, the presenter's `Text` and `MoveCaretToTextPosition`, then
  `CaretIndex`.
- **The test:** `TypedTextBoxDrawnTests` renders for real under Skia. It compares the typed box's ink with a box given
  the same text before it was shown, and fails on the old order (16 dark pixels, the caret alone, against 234).
