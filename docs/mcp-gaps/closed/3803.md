# Floating tools were selected and closed as dialogs — **CLOSED** (#3803, 2026-11-12)

**Symptom.** With Immediate floating, `take_snapshot {}` selected it and reported
`"activeDialog": "Immediate"`; `shutdown_ide {}` reported `"dialogsClosed": 1` and docked it back.
These calls were measured on Windows at 150% in the #3770 build d5bc91e6, as recorded in
[#3803](https://github.com/hexide-io/HexIDE/issues/3803). A failed path from an earlier IDE dump also
needed to explain how to reach a tool that had since floated; that part was reasoned in the issue.

**Workaround.** Use `take_snapshot {"window":"ide"}` for the IDE and
`take_snapshot {"window":"Immediate"}` for the floating tool. `shutdown_ide {"force":false}` follows
a person's exit without first closing other windows.

**Fix.** The factory's host-window type identifies the IDE's floating tools in both automatic selection
and forced shutdown. Explicit titles and unknown-name listings retain the floating windows. A failed
path in the IDE names floating tool windows and asks for a new `dump_visual_tree` with their title as
`window`; paths change when a tool moves to another window.

**Verification.** Factory-backed Linux headless tests exercise selection against the IDE and a running
form, real-dialog preference, title access and discovery, forced shutdown, and an actual path dumped
before floating. Live verification is delegated to the supervising session: repeat the calls above with
Immediate floating and confirm that shutdown does not dock it back before closing the IDE.
