# Tool-window paths depend on the IDE language — **CLOSED** (#3825, 2026-11-12)

**Symptom (measured in German in #3825).** These calls exposed translated title-bar paths:

```text
dump_visual_tree {"window":"ide","match":"TitleBar"}
inspect_element {"target":"Window/Custom[MainView]/Pane[DockControl]/Pane[Root dock]/List[PART_ItemsControl]/List[#0]/TitleBar[Locals]","window":"ide"}
```

The dump named `TitleBar[Werkzeugsammlung]`, `TitleBar[Lokal]`, `TitleBar[Überwachung]`,
`TitleBar[Eigenschaften]` and `TitleBar[Projekt - Project1]`. Inspecting English `TitleBar[Locals]`
failed and blamed floating `Direktbereich`, though Locals was docked.

**Workaround before the fix.** Discover paths afresh after every language, project-name or selected-tab
change, and address a floating tool by its translated window title.

**Fix.** Tool parts use `Tool.<layout key>` AutomationIds; translated automation names remain intact.
A single-tool title bar is `TitleBar[Tool.locals]`, with `Pane[Tool.locals]` beneath it. Shared chrome
uses `ToolGroup.<sorted keys joined by +>` (for example `ToolGroup.locals+watches`), so selecting another
tab preserves its identity. Its shown pane uses the selected tool's `Tool.<key>`. Moving tools between
groups still changes ancestor paths; dump again after a layout change. Document-region tabs use
`TabItem[Tool.languageServers]`. Keys include `toolbox`, `project`, `properties`, `formLayout`,
`immediate`, `locals`, `outline`, `watches`, `callStack`, `colorPalette`, `objectBrowser`,
`translationEditor`, `languageServers` and `protocolInspector`.

Add-in keys are the saved-layout keys, `addin:` followed by the tool's `Id`. The Id combines the add-in
id and the add-in's window id, so it survives restarts when the add-in supplies the same identifiers.
Discover the actual AutomationId instead of guessing an add-in id.

For example, after discovering a single-tool Locals pane, use
`TitleBar[Tool.locals]/Pane[Tool.locals]` in place of the translated segments above. A descendant
shortcut such as `Window/#Tool.locals` can be ambiguous because both chrome and pane carry that id;
use the typed segments from a dump. A floating tool accepts `window: "immediate"` in every language,
and the unknown-window refusal lists each floating host's keys beside its title. A floating hint is
limited to a failing segment naming a floating tool. Other failed segments in a non-English IDE
explain translated names and show stable-id examples.

**Verification.** Headless regression tests apply the German pack, round-trip tool paths, change the
selected tool, address a floating tool by key and check refusal guidance. Live Windows verification is
for the supervisor: repeat the calls above with Immediate floating in German; dump the stable paths,
inspect Locals, Properties and Project Explorer, change projects and selected tool tabs, and address
Immediate with `window: "immediate"`. No live check was run in this WSL task.

**Outside this fix.** `invoke_menu_item` and Dock menu paths still match display text, so German callers
must use the German labels: the pack names Object Browser `Objektkatalog` and the chrome Float
item `Schwebend` (access-key markers omitted here). This follows the matching code and German pack;
it was not live-measured in this run.
