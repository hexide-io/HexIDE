# An invoke reply misses a message box opened after an await — **CLOSED** (#5532, 2026-11-23)

**Symptom.** On Windows, `interact {"target":"Window/Custom/Button[Find Next]","action":"invoke","window":"Find"}`
reported only `invoked Button 'Find Next'`. The next `take_snapshot {"window":"ide"}` found the
end-of-search Yes/No message box already open. A caller could mistake the invoke for completed work
and send its next action behind that box. The Menu Editor's synchronous prompt was reported correctly.

**Workaround.** Follow an invoke whose command may be async with `take_snapshot` or
`dump_visual_tree` to discover a modal box before acting again.

**Fixed.** IDE button and menu invokes now wait for an exposed command task to finish or for a new
modal dialog, for up to two seconds. The existing `modalDialog` note names a box opened in that wait
as “opened during this call”. A task still running without a new dialog at the limit gets an explicit
unfinished-work note. Commands without a running task get one bounded Background dispatcher pass.
Find's three commands expose their tasks through the async `DelegateCommand` form; CommunityToolkit
async relay commands are also recognized. Headless tests exercise delayed modal creation through
`InteractAsync`, including commands that remain awaiting the dialog's answer. Live Windows verification
of the original Find Next sequence remains for the supervising session.

**What stays open.** A command that starts a task without exposing it can still reply before that task
finishes after the dispatcher pass. Other async-wrapped commands are converted one by one when such a
gap is met; this change converts only Find Next, Replace and Replace All.
