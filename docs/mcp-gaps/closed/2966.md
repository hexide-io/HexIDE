# `set_next_statement` said no project was running while an external debug session was paused — **CLOSED** (#2966, 2026-11-03)

**Symptom.** Measured by hexide-frm on 2026-11-03, in #2964's live check against RDCore `84278aea`'s debug adapter.
The external session had stopped on line 14, and `get_debug_state` replied
`{"running":true,"state":"Paused","stopReason":"breakpoint","module":"<workspace>\Module1.bas","line":14}`. Straight
afterwards, `set_next_statement {"module":"Module1","line":15}` replied
`{"success":false,"error":"No project is running","project":"Project1","document":"Module1"}`.

**Cause.** The tool read `ProjectRunnerService.RunningProject`, which only an interpreter run sets. `get_locals`,
`get_call_stack`, `evaluate` and the run-control tools all checked for an external session first, and this one didn't.

**Workaround.** None from automation. With #2964, Debug → Set Next Statement moves an external session's execution
point when its adapter offers goto targets.

**Fixed.** `set_next_statement` now checks `ExternalDebugger.IsActive` first, as its siblings do, and replies
"This command is not available for an external debug session." `ExternalSessionRefusalTests` reads every tool's body
and fails when a tool reads the debug controller or the running project before that check. With the check removed, it
fails on `set_next_statement`. Not checked live: this is the reply its siblings already gave there. #2968 tracks driving
an external session from these tools rather than refusing it.
