# answer_next_file_dialog said "the next file dialog" for a queued answer, and nothing about an open picker — **CLOSED** (#3913, 2026-11-14)

**Symptom.** Measured by hexide-docs on Windows in [#3913](https://github.com/hexide-io/HexIDE/issues/3913),
on a Debug build of main at `e6fb3b859`, while closing #2870's entry. Two answers armed in a row for Save
Project As, `answer_next_file_dialog(path: "<folder>\Form1.frm")` and then
`answer_next_file_dialog(path: "<folder>\Project1.vbp")`, both replied "The next file dialog will return …".
The second answer was queued behind the first, and answered the second picker. With Save Project As's
project picker left open, `answer_next_file_dialog(path: "<folder>\Project1.vbp")` replied the same way and
said nothing about the picker, which `invoke_menu_item`, `interact`, `clear_file_dialog_answers` and
`dump_visual_tree` report. Those notes also described a picker HexIDE gave no title as "title '(not specified)'",
though Windows shows it as "Save As".

**Workaround.** Count the answers already armed from `pending`, and check `clear_file_dialog_answers` for an
open picker before arming.

**Fix.** Arming returns the answer's place in the queue. Past the first, the note says, for example, "The 2nd
file dialog to open from now will return '…'. The answer armed before it is spent first." Every reply of the
tool, a refusal included, appends the open-picker note the other four tools give. A picker HexIDE gives no
title is described as "no title from HexIDE (the operating system shows its own, such as 'Save As' or
'Open')". Headless tests in `AnswerNextFileDialogNoteTests` cover all three.
