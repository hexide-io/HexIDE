# Breakpoint tools could neither set nor read conditions — **CLOSED** (#3810, 2026-11-12)

Symptom, recorded in [#3810](https://github.com/hexide-io/HexIDE/issues/3810) while checking #3796:
`set_breakpoints {"name":"QName","lines":[6]}` set a plain breakpoint, with no condition parameter in its
schema. `get_breakpoints {"name":"QName"}` returned `{"lines":[6]}` without any condition information.
The original report also called the gutter's Condition… unreachable (#3808); the issue correction
records that the right-click landed a line above the breakpoint after a code lens moved it.

Workaround: edit `codeBreakpointConditions` in `.user.hexproj` by hand, then read the saved sidecar or look
for a conditional glyph to see where a migrated condition went.

Fix: `set_breakpoints {"name":"QName","lines":[6],"conditions":{"6":"i = 3"}}` uses the gutter's
breakpoint-service condition API. `get_breakpoints {"name":"QName"}` now includes
`"conditions":{"6":"i = 3"}` and a note naming conditional lines. Omitting a condition key preserves
that kept line's expression; an explicit blank clears it.
The setter names expressions set or cleared;
a condition on a line absent from `lines` refuses everything. Plain replies retain `lines` and omit
`conditions`. Tool-level headless tests cover these cases and the generated schema's unchanged required
arguments and numeric property-name pattern (`^[0-9]+$`). Round-one live verification passed, as recorded
in the issue; round-two verification is left to the supervising session. No live check ran in this WSL task.

Syntax validation remains unchanged: the tool cannot reach `ParseValueStmt` through the IDE's
`IRunEngine` seam. `InterpreterSeamTests` forbids naming the interpreter directly from the server.
Invalid expressions are still accepted without a syntax warning, as permitted by the round-two brief.
