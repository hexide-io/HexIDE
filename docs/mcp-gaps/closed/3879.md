# Paste and Delete Line replies disagree with the code window — **CLOSED** (#3879, 2026-11-13)

Symptom: [#3879](https://github.com/hexide-io/HexIDE/issues/3879) measured
`press_key(target: <code window TextArea path>, key: "V", modifiers: "Ctrl")`
with selection offsets 73–105 and clipboard `ong`: the reply refused the mixed
selection while Edit/Paste replaced its editable portion. The same target with
`key: "Y", modifiers: "Ctrl"` on a locked Attribute line reported a press without
explaining that nothing was written.

Workaround: `invoke_menu_item("Edit/Paste")` replaced only editable text.

Fix: observe partial selections for paste, cut and Delete Line as well as
Delete/Back, and recognise the IDE keymap's Delete Line gesture when judging an
unchanged document after delivery. Indentation judges each selected line's start,
so Tab, Shift+Tab and the keymap's Indent chord name protected lines left
unindented even when the selection starts at column 1 of the declaration.
Delete Line reports the code removed and protected text left across the full
lines it takes. Partial-selection replies use single spaces, clean punctuation
and one caret offset, read after the editor settles. Ctrl+Shift+V has no binding. No editor-side
Delete Line or Redo behaviour is changed (#3880).

Round 1 verification: headless TypeKeysTests exercise the actual code window and replies: 61 passed,
with all six new cases failing against the original driver. Full Integration passed
3,559 with four existing #3869 skips; its xunit report records no errors.
Round 2 regression: the supervisor's live check found that selecting from

(and `modifiers: "Shift"`, or the keymap's Indent chord) indented code but
claimed no protected text stayed. Delete Line over protected and code lines
also omitted the partial-edit report. These replies now describe what stayed.
