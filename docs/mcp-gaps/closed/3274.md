# Hover on a running form omitted what the program printed — **CLOSED** (#3274, 2026-11-07)

**Symptom.** Measured on Windows on 2026-11-06 in [#3274](https://github.com/hexide-io/HexIDE/issues/3274):
`hover {"target":"Window/Button[Command1]","window":"Form1"}` raised a MouseMove handler that ran
`Debug.Print "move"`, but replied only `hovered (60.7, 20.7) through the window's input; no tip opened
within 1500ms`. The next `stop_project {}` reported `printed: "move\n"`.

**Workaround.** Read the Immediate window, or take the output from the next run-control reply.

**Fix.** Hover now watches the program before sending the move and waits for what it set off, using the
same ProgramPrinted tracker and reporting helper as interact, press_key and type_text. Its reply reports
output since the run began or the last reply that reported it, including a sentence when nothing was
printed. Design-mode hovers keep their previous replies.

**Headless verification (WSL, 2026-11-07).** All four `ProgramPrintedStartTests` cases pass. The two
hover cases use a running form and a yielding MouseMove handler, check printed output or the explicit
nothing-printed sentence, verify that stop does not repeat output, and keep design-mode replies unchanged.
With the pre-fix hover implementation temporarily restored, both hover cases fail at their output
assertions; the two Load cases still pass. The full integration suite passes 5,259 tests, with two
Windows font/GDI cases skipped and no xUnit fixture errors.

The original fixture tried to set Avalonia's application lifetime after initialization, which throws
before its cleanup scope and leaks its output subscription. The repaired fixture temporarily supplies
the desktop lifetime through its backing field for the real tool's window lookup, restores it in cleanup,
and subscribes to program output inside that cleanup scope.
