# `interact` `click` on a control scrolled out of view presses whatever covers that point, and reports success — **CLOSED** (#4558, 2026-11-18)

**Symptom.** Measured 2026-11-18 on Windows, on a Debug build of PR #4555's branch, with the Outline tool docked on a form's
code window. Filed as [#4558](https://github.com/hexide-io/HexIDE/issues/4558).

```
interact {"target": "Window/Custom[MainView]/Pane[DockControl]/Pane[Root dock]/List[PART_ItemsControl]/List[#1]/TitleBar[Tool.outline]/Pane[Tool.outline]/Custom/Tree/ScrollViewer", "action": "wheel", "value": "down"}      (twice: 0% to 52.1%, then to 100%)

inspect_element {"target": "Window/Custom[MainView]/Pane[DockControl]/Pane[Root dock]/List[PART_ItemsControl]/List[#1]/TitleBar[Tool.outline]/Pane[Tool.outline]/Custom/Tree/ScrollViewer/TreeItem[Form1]/TreeItem[Bump]"}
→ "boundingRect": [1012, 440, 244, 20], "isOffscreen": true        (the ScrollViewer is [1008, 492, 270, 132])

interact {"target": "Window/Custom[MainView]/Pane[DockControl]/Pane[Root dock]/List[PART_ItemsControl]/List[#1]/TitleBar[Tool.outline]/Pane[Tool.outline]/Custom/Tree/ScrollViewer/TreeItem[Form1]/TreeItem[Bump]", "action": "click"}
→ {"success":true,"mechanism":"pointer","detail":"clicked the left button at (122, 10) on 'TreeViewItem', which is (1134, 450)
   in the window; the press landed on 'Grid[PART_Grid]', which covers the target there; the pointer moved there first, as a
   person's does"}
```

The target never got the click: the Outline navigates on one, and the caret stayed where it was.
- **In view:** the same call landed on the item's `ContentPresenter[PART_HeaderPresenter]` and navigated.
- **Below the viewport, covered:** `Shape1` (`isOffscreen: true`) pressed a `TextBlock` and replied `success: true`.
- **Below the viewport, uncovered:** with nothing taking the pointer at the point, the call refused with `success: false`.

So whether a caller is told the truth depends on what happens to sit over the point. Read as a click, it nearly produced a false
product bug report: "the Outline doesn't navigate".

**Workaround.** Check `isOffscreen` with `inspect_element` before a `click`. If it's `true`, bring the item into view with
`wheel` on its scroll viewer first.

**Suggested fix.** For a target that a scroll viewer clips, call `BringIntoView` before pressing, as a person scrolls before
clicking. Failing that, refuse with `success: false`, naming `isOffscreen`. Either way, never report success for a press
that landed outside the target and its own parts.

> **Fixed.** `interact`'s `click` tests its press point against every clipping ancestor. A clipped point is brought into
> view first, and the reply says so, naming the scroll viewers that moved. If it's still clipped, the click refuses,
> naming what clips it, and presses nothing. A visible target under a cover still reports where the press landed, since a
> real click lands there too. Checked live on the Outline at 150% scaling: a click on an item with `isOffscreen: true`
> scrolled it into view, landed on its header and moved the caret to that procedure (#4558).
