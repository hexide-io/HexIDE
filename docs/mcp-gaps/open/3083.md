# No way to check a layout at 100% on a display scaled to 150%

**Symptom.** Measured on 2026-11-04 by the rdcore session during #3078's live check, on Windows Server 2025 with the
display at 150%. A check at 100% needs the IDE to run at scale 1, and nothing in HexIDE or its MCP tools sets that.
`AVALONIA_GLOBAL_SCALE_FACTOR=1` in the launch environment is ignored on Windows with Avalonia 12.0.5. With it set,
the IDE was launched through `scripts/dev-ide.ps1`. Then `set_window_state {"state":"Normal","width":860,"height":640,"x":0,"y":0}`
still answered `"scale": 1.5`, and `take_snapshot {"window":"ide"}` was 1290 × 960. `set_window_state` reports the
scale but takes no argument to change it.

**Workaround.** Mark the build's executable DPI-unaware for your user only. Add a string value `~ DPIUNAWARE`, named
with the exe's full path, under `HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers`. Windows
then reports 96 DPI to that exe, `set_window_state` answers `"scale": 1`, and Windows stretches the window to the
screen. Layout, overlap and alignment read as they would at 100%. Text is bitmap-scaled, though, so don't judge
glyph sharpness from it. Remove the value afterwards. It affects only that one exe path.

**Suggested fix.** A DEBUG-only launch flag, such as `--dpi-unaware`, that sets `Win32PlatformOptions.DpiAwareness`
to `Win32DpiAwareness.Unaware` in `Program.cs`. That does in-process what the registry value does. Avalonia 12.0.5
has the option, as read in its XML docs; nobody has tried it yet. A `scale` argument to `set_window_state` would not
work, because Windows fixes a process's DPI awareness at startup (reasoned, not checked). The flag gives scale 1
only, not fractional scales such as 125%. #3083 has the details.
