# VB6 Language Surface — What HexIDE Runs

> **Scope.** Every built-in of the VB6 *language*: statements, functions, operators, keywords and
> modifiers, literals and type names, compiler directives, intrinsic constants, and the in-box objects a
> program can touch without adding a reference. **1184 names**, each with HexIDE's current support level.
>
> **Sibling docs.** This is the *positive* inventory — what runs. The *gap catalogue*, which classifies
> why something is missing (Deferred / Walled / Platform / Partial), is
> [`interpreter-gaps.md`](interpreter-gaps.md); where they disagree, that one is authoritative on
> classification and this one on coverage. Verified runtime *semantics* live in
> [`vb6-fidelity-oracle/README.md`](vb6-fidelity-oracle/README.md). Debugger divergences are in
> [`debugger-vb6-divergences.md`](debugger-vb6-divergences.md). Permanently excluded features are in
> [`OUT_OF_SCOPE.md`](OUT_OF_SCOPE.md), and the IDE surface (menus, windows, designer) is
> [`MISSING_FEATURES.md`](MISSING_FEATURES.md).
>
> **Living document.** Update a row the moment its status changes.
> Diagnostic wording below reflects #935: missing-member messages omit receiver types, and value text
> prints inner type names without Either wrappers. This wording is HexIDE's, not a VB6 measurement.

## How to read this

The statuses are ordered by what a user experiences when they press **F5**, because that — not semantic
fidelity — is what decides whether someone keeps the IDE open. A missing statement is a cliff; a rounding
divergence is a footnote.

| Status | What happens on F5 | Why it ranks here |
|---|---|---|
| **Silently wrong** | Runs, does nothing or the wrong thing, program continues | **Worst of all.** Nothing announces it, so the user debugs their own correct code. |
| **Won't load** | The module never opens | Nothing runs, and the user cannot even look around. |
| **Dies** | Parses, then stops partway through with an error the user sees | The program gets going and falls off a cliff — but it *tells you*. |
| Partial | Runs, with a real restriction | Fine *if the restriction is written down* — which is what the Detail column is for. |
| No-op | Accepted and deliberately ignored | Acceptable only where ignoring it cannot mislead. See below. |
| Supported | Works for the ordinary case | |

**Why "Silently wrong" outranks "Won't load".** A file that will not open is obvious in a second, and the
user knows to blame the tool. A `Shell` that launches nothing, or a `Time = Now` that silently creates a
variable called `Time`, sends someone hunting through their own logic for a bug that is ours. That is the
same harm shape as a silently lossy save, which
[`serialization-outcomes.md`](serialization-outcomes.md) rules out entirely.

**The mechanism, because it generalises.** An unregistered bare name is not an error in VB6's default
configuration and was not one here either: it fell through to implicit declaration and evaluated to
`Empty`, so `s = CurDir` yielded Empty rather than raising, with only the `Option Explicit` path — **off
by default**, as it was in VB6 — turning it into an error. Every intrinsic *called bare*, without
parentheses, was therefore a candidate for this category rather than for Dies.

**That mechanism is closed** as of [#191](https://github.com/hexide-io/HexIDE/issues/191): both the read
path and the bare-statement path now raise for any name VB6 defines as an intrinsic, keyed off a list of
VB6's *surface* rather than of our gaps — so implementing a function needs no edit to it, and a name we
have never heard of still gets VB6's own "Sub or Function not defined".

The category was kept at zero rather than deleted, because the shape is what matters: **anything that
fails without saying so belongs here rather than under Dies.** It did not stay at zero. Assignment through
a type character (`s$ = "x"`) was found doing exactly that by a different mechanism, and the six type
characters now sit in it ([#739](https://github.com/hexide-io/HexIDE/issues/739)).

**Until [#754](https://github.com/hexide-io/HexIDE/issues/754), most Dies rows told only the test suite.**
The classification above was made by running constructs headlessly, where the exception reaches the test.
In a running IDE, how a row dies decides whether the user hears about it:

- **By `NotImplementedException`, which is most of them, or by any other .NET exception.** A form's event
  procedures and `Sub Main` both stopped at a catch that only logged, so a click handler ended part way
  while the program carried on, and F5 on a `Sub Main` project opened nothing. Until #754 these rows were,
  at the keyboard, Silently wrong. Now the run ends and the runtime-error dialog says what HexIDE does not
  implement, or reports VB6's Internal error (51) with the .NET exception for the rest. Neither is
  trappable, because `On Error Resume Next` stepping over a statement that never ran would be a wrong
  result rather than a late error.
- **By a VB6-shaped error** (a numbered run-time error, a compile error, or a "Run-time error" with no
  number). These were already shown. The ones with no number can still be trapped, and under
  `On Error Resume Next` they are skipped with `Err.Number` left at 0. That is Silently wrong under an
  error handler, and it is tracked in [#257](https://github.com/hexide-io/HexIDE/issues/257).

**Not every absence is safe to demote into No-op.** `DoEvents` returning 0 without pumping messages, as it
did until #766, withheld a behaviour and lied about nothing. `Print #` as a no-op would silently not write the user's
file — the same harm shape as a silently lossy save, which
[`serialization-outcomes.md`](serialization-outcomes.md) rules out entirely. So the question for each gap
is not only *how expensive to close* but *can it be degraded honestly in the meantime*.

`Beep` is the cautionary tale in the other direction: it sat as a no-op justified by cross-platform
concerns until someone checked, and the justification was simply wrong — `Console.Beep()` is unsupported
only on platforms HexIDE does not ship to. It is now implemented. Before accepting a No-op row here,
check whether the reason still holds.

## Two things this document is not

**Nothing here is `vb6.exe`-verified.** The classification ran while the oracle VM was unreachable, so
every row is derived from reading HexIDE's own source, not from measuring real VB6. That is sound for
*does it run* — a `NotImplementedException` is a fact about our code — but it is **not** authority on
*does it behave correctly*. Where a Partial row describes a semantic difference, treat it as a lead to
verify, not a measurement. Verified behaviour only ever lives in
[`vb6-fidelity-oracle/README.md`](vb6-fidelity-oracle/README.md). A row re-rated since on the oracle's evidence names
the oracle rows it rests on, and says which parts no oracle row covers; for the type characters, the
Silently wrong section does.

**"Supported" is an optimistic ceiling.** Every row was attacked by an adversarial pass whose only job
was to disprove it. It returned a verdict on 323 originally-supported rows and **demoted 217 of them** —
**two thirds**. It did not reach all of them. So read Supported as *no one has yet shown this broken*,
and expect the real figure to be materially lower.

A worked example of what that means in practice: this document downgraded `Split` and `Filter` for
mishandling omitted optional arguments, and left `Join` as Supported — even though `Join` uses the *same*
`HasArg` helper, three lines away in the same file. The demotions are as incomplete as the attacks were.

**These statuses were derived by reading code, then corrected by execution where a verifier bothered to
run something.** Where a row says a construct throws, that is usually solid. Where it says something
*works*, treat it as a lead.

**The sweep is a snapshot, and work landed after it.** Rows overtaken since are marked inline with
**Superseded by #N**, rather than quietly rewritten, so it is visible which parts are second-hand. The
known case is [#184](https://github.com/hexide-io/HexIDE/pull/184), which made object member chains fold
on the *read* path — seven rows describe the single-dot restriction it removed. #822 (#1056) lifted it for
`obj.a.b = x` too, and it now survives only for `Set obj.a.b = o`.

### The single most useful number here is 1

**Only one construct in this inventory fails to parse**: a `Function` declared with a type
character (`Function GetName$()`, [#740](https://github.com/hexide-io/HexIDE/issues/740)). Every other
gap parses cleanly and goes wrong at run time: mostly by throwing, sometimes by running on with a wrong
value. The seven Silently wrong rows below are the wrong values counted as such; the `()` row records
another under [#741](https://github.com/hexide-io/HexIDE/issues/741) and stays Partial, for the reason
given there. The grammar comprehends essentially the whole of VB6; what is missing is execution.

It was four until numeric line labels were ported in from the LSP server's grammar, which already had
the rule — see below. It went back to four when the suffixed `Function` was measured, and that one has
the same shape: the LSP server's grammar accepts it and the interpreter's does not. It went to two when
conditional compilation took `#Const` off it ([#1112](https://github.com/hexide-io/HexIDE/issues/1112)): the directives are applied to the module's text
before the parse, so the grammar never sees one, as vb6.exe's parser never sees an inactive branch. The `D` exponent
marker left it when vb6.exe was found to compile one ([#1611](https://github.com/hexide-io/HexIDE/issues/1611)), and the same measurement found a
literal ending in its point, which took its place. That went to one when both grammars learned to read it
([#1615](https://github.com/hexide-io/HexIDE/issues/1615)).

That matters for three reasons. It is the empirical form of the claim in `CLAUDE.md` that no VB6
construct is incomprehensible to the CST, which until now was an architectural assertion rather than a
measurement. It means a user opening real VB6 source will nearly always *see* their code, correctly
highlighted, with working navigation, even where it will not run — a far better first impression than a
file that refuses to open. And it means the remaining work is almost entirely additive: implementing a
visitor, not changing how the language is understood.

### Where the damage actually is

**Operators are nearly complete** — 1 absent of 32 — so expressions and arithmetic generally work. The
damage is concentrated in **statements** and the **in-box object model**: 17% of VB6's statements (18
of 107, two of them the `Function` rows, which fail only when a type character is used) and 67% of the
in-box surface (`App`, `Screen`, `Printer`, `Clipboard`; 82 of 123) are unavailable. Both
figures are rounded to the nearest whole percent.

That is the honest answer to "will my code run?" — the arithmetic will; the plumbing around it often will
not. Text files run since [#1145](https://github.com/hexide-io/HexIDE/issues/1145): `Open` For Input, Output and
Append, `Line Input #`, `Print #`, `Close`, `FreeFile` and `EOF`; `Input #` and `Write #` since
[#1521](https://github.com/hexide-io/HexIDE/issues/1521); `Kill`, `Dir` and the other filesystem statements since [#1561](https://github.com/hexide-io/HexIDE/issues/1561). Still absent as a block:
`LOF`, `Loc`, `Seek` and the `Input` function run since
[#1645](https://github.com/hexide-io/HexIDE/issues/1645), and Random and Binary files, `Get` and `Put` since [#1646](https://github.com/hexide-io/HexIDE/issues/1646).

## Silently wrong — 7 names

**The six identifier type characters, `$ % & ! # @`
([#739](https://github.com/hexide-io/HexIDE/issues/739)).** An assignment through one writes a
*different* variable, and the program runs on with the value lost. Measured here without
`Option Explicit`, which is VB6's default, with VB6's answer from the same configuration beside each
except where a bullet says otherwise:

- `Dim s As String : s$ = "x" : Debug.Print s` prints `""`, and the same inside a `Sub`. VB6 gives the
  assigned value, for a module variable and a local alike.
- `n% = 5` into an Integer, `l& = 70000` into a Long, `f! = 1.5` into a Single, `d# = 2.5` into a Double
  and `c@ = 1.25` into a Currency each leave the declared variable at `0`. VB6 gives 5, 70000, 1.5, 2.5
  and 1.25, each in the declared type.
- `Dim i As Integer / For i% = 1 To 2 / Next / Debug.Print i` prints `0`, and a bare `i` read inside the
  loop reads `0` on both passes. VB6 leaves `i` at 3, with and without `Option Explicit`, measured
  for a local `i`; VB6's module-level counter is not measured. `Next i%`
  throws here instead ("TypeHints not implemented"). This one is silent under `Option Explicit` too.
- With nothing declared, `a$ = "x"` followed by a bare `a` reads `Empty`. VB6 gives `"x"`, a String:
  `a$` and `a` are one variable. VB6 does the same for every character; HexIDE's side of the undeclared
  case was run for `$` only.

`VisitLetStmt` in `StatementExecutor.cs` names the target by its full text, character included
(`GetText()`), so it looks up a variable called `s$`, finds none, and creates one, because
`Option Explicit` is off by default. `VisitForNextStmt` takes its counter's name the same way. Both are
read from the source; the probes measured what follows from them. **So the assignment is silent only
without `Option Explicit`.** With it, `VisitLetStmt` raises "Variable not defined" for the suffixed name
instead (`s$`, `n%`, `l&`, `f!`, `d#` and `c@`, each measured), an error VB6 does not raise. The `For`
counter is the exception: `VisitForNextStmt` allocates its counter without that check, so under
`Option Explicit` too `For i% = 1 To 2` leaves a declared `i` at 0 with no error, measured at module level
and inside a `Sub`.

VB6 sends the assignment to the declared variable for all six characters, into a module variable and
into a local, with `Option Explicit` and without it: every one of those combinations is measured, in the
section "An assignment through a type character reaches the declared variable, for every character"
of the 2026-10-11 entry "A type character on a name the program also declares" in [`vb6-fidelity-oracle/a-type-character-on-a-name-the-program-also-declares-left-beside-a-user-left.md`](vb6-fidelity-oracle/a-type-character-on-a-name-the-program-also-declares-left-beside-a-user-left.md). The same entry measured it first
for `$` on a name with a library twin, `Left` (TF_01, TL_01, TL_04). With nothing declared, the first
assignment through a character declares the variable with that type, for every character: `a$ = "x"` then
`a` gives `"x"` String, `k% = 3` then `k` an Integer 3, and `&`, `!`, `#` and `@` a Long, Single, Double
and Currency. So the undeclared case is wrong here too, and is counted: HexIDE's side of it was run for `$`, and the
other five go through the same `VisitLetStmt` path, which is read from the source rather than run.

**Why the write is the silent one.** Every unqualified *read* through a type character throws —
`Debug.Print s$` gives "Type hint is not supported" ([#742](https://github.com/hexide-io/HexIDE/issues/742))
— so the one use that announces nothing is the one that changes state. A module-qualified read is the
other exception, and a milder one: the qualifier path drops the character unchecked, so `Module1.VF$("x")`
answers here where VB6 refuses to compile it. That is a missing error, not a wrong value (#742). The reverse order is a late error, not a wrong
one: `b = "y"` with nothing declared, then `b$`, is the compile error "Type-declaration character does not
match declared data type" in VB6, because the bare first use declared a Variant, and here the read
throws. The literal forms are unaffected: `5%`, `70000&`, `1.5!`, `2.5#` and `1.25@` measure as Integer,
Long, Single, Double and Currency. `$` has no literal form.

**Measured, and recorded under [#741](https://github.com/hexide-io/HexIDE/issues/741) rather than here:
call resolution.** A parameterless `Function Left() As String` called as `Left("abc", 1)` returns the
program's own value here, where VB6 compiles the call and returns the library's `"a"` (TE_01). The same
function without an `As` clause returns its value here with no error, where VB6 compiles the call and
raises error 13 at run time (TE_04). TE_01 is a wrong result from a program VB6 runs; TE_04 is a missing
run-time error, not a wrong result. TE_01 needs a parameterless procedure that shares a library
function's name and is called with that function's arguments, since the library supplies VB6's answer;
whether TE_04's needs the name too is open (see the `F` bullet below). Rating the call operator itself Silently wrong for
TE_01 would misdescribe the common case, which resolves correctly, so it is recorded under #741 and the
`() (call / array index)` row stays Partial and carries the link. Two neighbours in the same issue, both
missing errors rather than wrong results:

- `Dim Left As String` followed by `Left("abc", 1)` reaches the library's `Left` here, where VB6 refuses
  to compile it with "Expected array" (TL_07; TF_04 for a module variable).
- Surplus arguments are dropped, where VB6 refuses to compile the call. `H(5, 6)` on
  `Function H(ByVal a As Long) As Long` gives 5 here, and `G(5, 6)` on a parameterless
  `Function G() As Long` gives 1; for both, VB6 gives the compile error "Wrong number of arguments or
  invalid property assignment". `F(5, 6)` on a parameterless `Function F()` with no `As` clause gives 1
  here, and VB6 gives the compile error "Expected array", where TE_04, the same shape named `Left`,
  compiles and raises error 13; `F` ran in the scripted harness and TE_04 in a project, so whether the
  name or the harness makes that difference is open. None of the three raises anything here. (Oracle: the 2026-10-11
  entry "A type character on a name the program also declares", the surplus-argument rows beside TE_01–TE_04.)

**Closed earlier by [#191](https://github.com/hexide-io/HexIDE/issues/191).** Eight constructs used to
sit here: `Shell`, `FreeFile`, `Command`, `CurDir`, `Cls`, `Erl`, `Dir` and `Time = x`. Each parsed, ran,
did nothing, and let the program continue — so the user saw no error and went looking for a bug in their
own code.

Two causes, both now fixed. An unregistered bare name fell through to VB6's implicit-declaration rule and
evaluated to `Empty`; the read path now raises for any name VB6 defines as an intrinsic, and the
bare-statement path no longer discards the "not a builtin" result. And `Time = x` was grammar-shadowed —
`TIME` is an ambiguousKeyword and `letStmt` was matched ahead of `timeStmt`, so it silently created a
*variable* called `Time` and left the throw in `VisitTimeStmt` as unreachable dead code. `dateStmt`
already sat ahead of `letStmt`, which is the only reason `Date = x` threw and `Time = x` did not.

**The category stayed in this document at zero**, because it is the failure mode worth watching for:
anything that fails without saying so belongs here rather than under Dies, and the reasoning above is how
to recognise the next one. The check keys off a list of VB6's *surface* rather than of our gaps, so
implementing a function does not require maintaining it. It could not have caught the type characters,
which are the program's own names spelled with a suffix rather than names VB6 defines.

**A standard module's Property Get is not reached by its name ([#977](https://github.com/hexide-io/HexIDE/issues/977)).** `x = PG`, with
`Property Get PG() As Long()` in a standard module, reads Empty here with no error, where VB6 reads the array; the name
is taken for an undeclared variable. Found while fixing #975. A class's Property Get is unaffected.

## Won't load — 2 names

The whole list. A parse failure takes the entire module down — nothing in the file runs and the editor
cannot open it usefully — so despite how obscure these look, each one has a blast radius of a file rather
than a statement. That is why they are worth fixing ahead of far more commonly used constructs that merely
throw.

**`Function` joined the list by measurement** ([#740](https://github.com/hexide-io/HexIDE/issues/740)).
A `Function` declared with a type character, `Function GetName$()`, does not parse; without one it does,
so its two rows, `Function` and `Function...End Function`, are rated by that worst case. They are two
names for one construct, as `Line number` and `LineNumber` are. Unlike the others it does not look
obscure: the character stands in for an `As` clause. Only `$` has a VB6 row: VB6 compiles a `Function`
declared with it (oracle TR_01, TR_02, TB_01, each a `Function Left$`). No oracle row has a `Function`
declared with `% & ! # @`, although HexIDE refuses `Function Twice%` in the same way.

**A literal ending in its point, and the `D` exponent, used to be here.** vb6.exe compiles `5.` and `5.D1`, and both
grammars needed a digit after the point and lexed no `D` in a whole number. Both were measured and are read now
([#1611](https://github.com/hexide-io/HexIDE/issues/1611), [#1615](https://github.com/hexide-io/HexIDE/issues/1615)).

**Multiple file numbers on one line used to fail here** ([#1146](https://github.com/hexide-io/HexIDE/issues/1146)).
The date-literal token swallowed the text between two `#`s, so `Line Input #1, s: Print #2, s` and
`Close #1, #2` prevented a whole module from parsing. Both grammars now delimit date/time components instead of
arbitrary text. Real dates still win where VB6 gives them that meaning: `#1, 2#` is a date, even after `Print`.

**Numeric line labels used to be here**, and how they were found is the useful part: the LSP server's
grammar already had a working `lineNumber` rule that the interpreter's lacked, so the *editor* accepted
`10 Debug.Print 1` with no syntax error and the module then refused to load. HexIDE's two halves
disagreed about what VB6 is. `GrammarParityTests` now compares the two rule inventories so the next such
gap is a build failure rather than a bug report. It compares inventories, though, not what each rule
accepts, which is how the suffixed `Function` got past it: both grammars have a `functionStmt`, and only
the LSP server's lets a type character follow the name.

Worth noting what is *not* here: `#If` parsed fine and threw, an execution gap rather than a grammar gap,
which is the cheaper kind to close. It runs since [#1112](https://github.com/hexide-io/HexIDE/issues/1112), with `#Const`, and the named-argument
operator `:=`, the other such gap, since [#1465](https://github.com/hexide-io/HexIDE/issues/1465).

## Intrinsic constants — 621 names in 89 families

Constants are half the language surface by count and would swamp a table, so they are summarised by
family. They also have almost no nuance individually: a constant either resolves to the right value or it
does not.

**They resolve as VB6 resolves them.** In VB6 these are not flat constants: they are members of *enums*,
and of one *module*, published by the VBA and VB type libraries (`ColorConstants`, `VbMsgBoxStyle`,
`KeyCodeConstants`, `VbVarType`, `VBA.Constants` and so on), which is why the Object Browser was full of
them. Since [#215](https://github.com/hexide-io/HexIDE/issues/215) HexIDE resolves each through its library, from a dump of the real type libraries: bare,
qualified by its library (`VBA.vbCancel`) or its container (`VbMsgBoxResult.vbCancel`) or both, and an
in-box enum is a type (`Dim x As VbMsgBoxResult`). `InBoxConstantTests` runs each form.

This section went on describing the flat name-to-value table #215 replaced, in which no enum type was
registered, for weeks after it stopped being true, and eight rows were rated Dies on that reading ([#1633](https://github.com/hexide-io/HexIDE/issues/1633)).

**The Object Browser still shows none of them.** Its VBA library is built solely from the LSP
`vb/builtinSymbols` response, which enumerates `VbSignatures.GetAll()` — a 97-entry list that contains no
constant. So it lacks not merely the *grouping* but every intrinsic constant.

The larger cause of Partial is a constant whose **consumer** is absent: a correct value that nothing can
use. Be careful reading these rows, though — the grading is inconsistent on exactly this point. The
raster-op family is graded Supported although `PaintPicture` does not exist, while the OLE and mouse-
pointer families are graded Partial for the same reason. The difference records which rows an adversarial
pass happened to attack, not a real distinction.

## The signature-help trap

A name the IDE describes is not a name the interpreter runs. `VbSignatures.cs` in the LSP server is
**editor metadata with no execution path**: it feeds signature help and the `vb/builtinSymbols` response
that populates the Object Browser's VBA library. Thirteen names are listed there, offer a full
parameter tooltip, and then fail at run time:

`StrComp`, `CVar`, `CVErr`, `Shell`, `Environ`, `IIf`, `Choose`, `Switch`, `AscW`, `ChrW`, `CreateObject`,
`GetObject`, `CLDbl`.

`CLDbl` is not a VB6 function at all. `Randomize` and `Err` are listed there too, and do work: one is a statement,
the other an object. `RGB` and `QBColor` were on this list until they were implemented. Counted by comparing that
file's names with the interpreter's registry, not by hand.

Worse than a plain gap, because the IDE vouches for the call before the user makes it. Closing the gap
between those two lists — implement it, or stop advertising it — is cheap and disproportionately improves
how the IDE feels.

**A name the tooltip shows is not one VB6 takes by name, either**
([#1465](https://github.com/hexide-io/HexIDE/issues/1465)). Twenty intrinsics refuse every named argument, as a
"Syntax error", although signature help names their parameters: `Len(Expression:="abc")` does not compile (oracle,
"Named arguments"). So the interpreter keeps its own table of the names it takes, `VB6BuiltIns.NamedParameters.cs`,
measured, and `NamedParameterParityTests` holds it to `VbSignatures.cs` in one direction. Every name the interpreter
takes must be the name the tooltip shows, in the tooltip's order; the tooltip may show names VB6 refuses. Every intrinsic
the interpreter implements is in one of its tables and has a tooltip, and the same test fails when one is added without
both ([#1475](https://github.com/hexide-io/HexIDE/issues/1475)).

**Autocomplete itself is not the culprit**, contrary to an earlier draft of this section. Completion is
served from a different list (`VbKeywords.All`), and none of the thirteen appears in it. The trap is
signature help and the Object Browser, not the completion popup.

## Not yet enumerated

The sweep behind this document did not reach everything, and a coverage document that implies otherwise is
worse than one that says where it stops. Known holes, none of which have rows anywhere above:

| Area | Missing |
|---|---|

| In-box classes | **#2062:** a .frm control without its own Font block receives a load-time copy of the form font, including inside nested Frames/PictureBoxes; explicit blocks stay intact. `FontName`/`FontSize` read that copy. Designer rendering and UserControl contents remain unmeasured. `Form`, `MDIForm`, `UserControl`, `Menu`, `VBControlExtender`, `StdFont`, `StdPicture` — the classes the enumerated members hang off. |
| Extender methods | `Move`, `ZOrder`, `SetFocus`, `Refresh`, `Show`, `Hide`, `PopupMenu`, `Arrange`, `ShowWhatsThis`. Not enumerated, though `Move` on a control runs since #1071 (oracle, "Move, ScaleWidth and ScaleHeight") and on a form since #1569 (oracle, "A form's Move"), `SetFocus` since #1061 (oracle, "SetFocus"), and `ZOrder` on a control since #1503 (oracle, "What ZOrder does at run time"). |
| Graphics methods | `Point`, `PaintPicture`, `TextWidth`, `TextHeight`, `ScaleX`, `ScaleY` (and `Line` appears only as a statement, not in its graphics form). |
| Printer methods | Every `Printer` row is a *property*; `Printer.Print`, `.NewPage`, `.EndDoc`, `.KillDoc`, `.Line` are absent. |
| Drag and drop | `Drag` and `OLEDrag` — the methods the enumerated drag constants are arguments to. |

The events gap is the largest and the most consequential: event handlers are how a VB6 form program is
structured, so a coverage document that omits them is silent about the most-used surface in the language.

changes, edit the row. When adding a construct, add its row in the same change — a coverage document that
drifts is worse than none, because it is quoted rather than checked.

this document's first draft had every `StatementExecutor.cs` citation off by 29 lines because a commit

the anchor — it is greppable and it moves with the code. Please do not add line numbers back.
