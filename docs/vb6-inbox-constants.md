# VB6's in-box constants, by declaring library

Every enum member and module constant in the four type libraries a VB6 Standard EXE references by
default — **728 constants, across 77 enums and 2 constant modules** — read out of the real libraries
rather than transcribed from documentation.

Generated by [`scripts/dump-typelib-constants.ps1`](../scripts/dump-typelib-constants.ps1) via
`LoadTypeLibEx` with `REGKIND_NONE`. **Do not hand-edit — regenerate.** The machine-readable form is
[`vb6-inbox-constants.json`](vb6-inbox-constants.json).

| library | description | enums | enum members | const modules | module constants |
|---|---|---|---|---|---|
| `VBA` | Visual Basic For Applications | 14 | 117 | 1 | 11 |
| `VBRUN` | Visual Basic runtime objects and procedures | 61 | 590 | 1 | 3 |
| `stdole` | OLE Automation | 2 | 7 | 0 | 0 |
| `VB` | Visual Basic objects and procedures | 0 | 0 | 0 | 0 |

## Four findings that a flat name→value table cannot express

**1. `VB` declares no constants at all.** This is the reasonable guess got wrong: the *control*
constants — `AlignConstants`, `BorderStyleConstants`, `ScaleModeConstants`, `MousePointerConstants` —
are not in "Visual Basic objects and procedures". They are all in **`VBRUN`**, which holds 590 of the
728. `VB` contributes zero.

**2. VBRUN is not a file.** It shares `MSVBVM60.DLL` with `VBA` and is reachable only as typelib
resource **`MSVBVM60.DLL\3`** (`VBA` is index 1). A tool that enumerates library *files* finds `VBA`
and silently misses 81% of the constants.

**3. The library qualifier SELECTS — it is not decoration.** Exactly one name of the 728 is declared
twice with two different values, and VB6 resolves each qualified form to its own library's value:

| written | VB6 |
|---|---|
| `vbCancel` | **2** |
| `VBA.vbCancel` | **2** |
| `VBRUN.vbCancel` | **0** |
| `VBRUN.DragConstants.vbCancel` | **0** |

`vbCancel` is `2` in `VBA.VbMsgBoxResult` and `0` in `VBRUN.DragConstants`. The bare form resolves to
VBA's, so reference order gives VBA precedence. **A flat table must answer one of these four wrongly.**

The only other duplicated name, `vbNormal`, is `0` in both `VBA.VbFileAttribute` and
`VBRUN.FormWindowStateConstants` — consistent, and therefore harmless. That contrast is why the
`vbCancel` result is attributable to the *disagreement* and not to duplication as such.

**4. An in-box enum is a TYPE, not just a bag of values.** `Dim x As VbMsgBoxResult` is legal
(measured). So each of these 77 names has to be resolvable in type position, which a constant table
cannot do at all.

## Enum member vs module constant, and why the split matters

VB6 puts constants in *both* kinds of container, and the kind decides how a name may be addressed: an
**enum** name is both a type and a qualifier, a **module** name is only a qualifier. `VbVarType.vbLong`
is an enum member; `Constants.vbCrLf` is a module constant. A collector that walked only `TKIND_ENUM`
would omit the entire `vbCrLf` family — 11 constants including `vbTab`, `vbNullString` and `vbNewLine`.

Their values are not all numbers, which is the other reason they need separate handling: measured,
`vbTab` is `Chr(9)`, `vbBack` `Chr(8)`, `vbVerticalTab` `Chr(11)`, `vbFormFeed` `Chr(12)`, `vbNullChar`
`Chr(0)`, `vbNewLine` is CRLF (length 2), and `vbNullString` has length 0 — though `vbNullString` is
semantically a null pointer rather than `""`, a distinction that only becomes visible when passing it
to a `Declare`.

## Where HexIDE stands against this

`VB6BuiltIns.builtInConstants` is a flat, library-blind `Dictionary<string, Vb6Value>`. Measured
against the inventory:

- **709 of its numeric values are correct** and every one of them is a real constant from one of these
  four libraries — no invented names.
- **`vbCancel` is declared twice in the C# initializer**, `= 0` at one line and `= 2` at another.
  Indexer-style collection initialization does not throw on a duplicate key: the later assignment
  simply wins, so the value is decided by declaration order. It currently lands on `2`, which is right
  for the bare form by accident rather than by rule.
- **The library and enum qualifiers are treated as transparent** — looked past, then the bare name
  resolved — so `VBRUN.vbCancel` and `VBRUN.DragConstants.vbCancel` both answer `2` where VB6 says `0`.
- **None of the 77 enum names is known as a type**, so `Dim x As VbMsgBoxResult` cannot work.
- **7 members of `VBA.Constants` are absent entirely** — `vbTab`, `vbBack`, `vbFormFeed`, `vbNewLine`,
  `vbNullChar`, `vbNullString`, `vbVerticalTab`. `vbTab` and `vbNullString` are already recorded as
  **Dies** in [`MISSING_LANGUAGE.md`](MISSING_LANGUAGE.md).

## A transport trap, recorded because it nearly shipped

The first version of the generator emitted tab-separated text, and it reported **`vbTab`'s value as the
empty string**. `VBA.Constants` is the one container whose values *are* control characters — `vbTab` is a
tab, `vbCrLf` a CRLF, `vbLf` an LF, `vbNullChar` a NUL — so a tab-separated transport ate or split exactly
the eleven rows that mattered, and did it silently: the row counts came out identical and every numeric
constant was unaffected. The generator now emits JSONL with every control character escaped.

The values below were then confirmed a second, independent way — a compiled VB6 program reporting
`Asc(vbBack)` = 8, `Asc(vbFormFeed)` = 12, `Asc(vbVerticalTab)` = 11, `Asc(vbNullChar)` = 0,
`Len(vbNewLine)` = 2 and `Len(vbNullString)` = 0 — which agrees with the type library exactly. Worth the
belt and braces: a measurement that has passed through a lossy format looks exactly like a correct one.
