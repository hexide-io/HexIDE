## Long lines, line continuations and long expressions (2026-11-06, #3202)

**The question.** How long can a VB6 statement be? Three limits were asked about: line continuations, the length of
one physical line in a `.bas` written outside the IDE, and the size of one expression, as an operator chain or as
nested parentheses. Asked because the #1368 corpus has deep-chain rows, 10,000-term chains, whose expected value is
Error 28 (Out of stack space). That value is HexIDE's own guard from #1930, which said VB6's limits were unmeasured.

**The obvious guesses, and what VB6 did instead:**
- **A very long expression would fail when it runs,** with Out of stack space, or with "Expression too complex". It
  never runs. VB6 refuses it when it compiles, with **"Statement too complex"**, and in the IDE that happens when
  the module loads. Every case that compiled ran to the right value, with no run-time error of any kind.
- **1,023 characters would be a hard limit on a line.** A longer physical line loads. VB6 reads it in pieces of
  1,023 characters, and each piece after the first counts as a line continuation.
- **The expression limit would be a number of terms.** It isn't. The same 2,553-term chain builds or is refused
  depending on how it is laid out in lines.

None of the corpus's 10,000-term shapes can be written in a form vb6.exe accepts.

### The probe

VB6 6.0 SP6 (VB6.EXE 6.00.9782) on the Windows 10 oracle guest. Each case was a Standard EXE whose only module was
this, with the probe's lines where `v = ...` stands:

```vb
Attribute VB_Name = "Module1"
Option Explicit

Sub Main()
Dim f As Integer, v As Variant
f = FreeFile
Open App.Path & "\" & App.EXEName & ".txt" For Output As #f
On Error Resume Next
Err.Clear
v = ...
Print #f, "v=" & Left$(CStr(v), 20) & "|len=" & Len(CStr(v)) & "|" & TypeName(v) & "|err=" & Err.Number
Close #f
End Sub
```

The source was ASCII with CRLF line ends, generated by a script so that every line length is exact. Each case was
built three ways:
- **Native code:** `vb6.exe /make`, with `CompilationType=0`.
- **P-code:** `vb6.exe /make`, with `CompilationType=-1`.
- **The IDE:** `vb6.exe /run`, which loads the project and runs it as p-code. Every message box was logged with its
  text, then dismissed with OK.

Whatever built was run, and its file read back. Most chains sum ones, so the value shows whether every term was
read.

**185 cases were built both as native code and as p-code, and the two agreed on every one.** 22 of them were also
run in the IDE, which agreed with `/make` on all 22. So the tables below give one answer for all three builds.

### Line continuations

One term to a line, `v = 1 + _`, then `1 + _`, and so on.

| Continuations | `/make`, native and p-code | The IDE |
|---|---|---|
| 23 | builds, and runs to 24 | |
| 24 | builds, and runs to 25 | runs to 25 |
| 25 | **"Too many line continuations"** | the same, at load; see below |
| 26 | "Too many line continuations" | |

**`/make` reports this one differently from a syntax error.** A syntax error is reported as `Compile Error in File
'...', Line n : Syntax error` followed by `Build of '...' failed.`. "Too many line continuations" came alone, with no
file, no line and no "Build failed" line. "Statement too complex", below, came the same way. `/make` exited with 1
in all three.

**In the IDE, the refusal comes at load and costs the rest of the module.** Opening the project, without running it,
raised two boxes:
- "Too many line continuations";
- "An error occurred while background loading module 'Module1'. Background load will now abort and the code for some
  modules may not be loaded. Saving these modules to their current file name will result in code loss. Please load a
  new project."

The code window then held the module up to `Err.Clear` and nothing after it. The refused statement, the two lines
after it and `End Sub` were gone. Run then failed with "Compile error: Expected End Sub".

### One long physical line

| The probe line | Where character 1,023 falls | `/make`, native and p-code | The IDE |
|---|---|---|---|
| `v = 1 + 1 + ...`, 1,022 characters | | builds, 264 | 264 |
| the same, 1,023 characters | | builds, 354 | 354 |
| the same, 1,024 characters, ending `+ 1000` | **inside `1000`** | **Syntax error** | Syntax error |
| `v = 1000 + 1 + ...`, 1,024 characters | at a space | builds, 1254 | 1254 |
| `v = 1 + 1 + ...`, 1,025 characters | between `+` and a space | builds, 256 | 256 |
| `v = 1 + 1 + ...`, 5,000 characters | four cuts, each between tokens | builds, 2248 | |
| `v = "xx...x"`, 1,022 and 1,023 characters | | builds, Len 1016 and 1017 | |
| the same, 1,024, 1,025 and 5,000 characters | inside the string literal | Syntax error | 1,024: Syntax error |

A long line raised no box at load. Where the cut split a token, the Syntax error came at Run.

**The pieces count as continuations.** In these the cuts all fall in a run of spaces, so no token is split:

| The probe line | `/make` | The IDE |
|---|---|---|
| `v = 1`, spaces, `+ 1`: 25 x 1,023 = 25,575 characters | builds, 2 | 2 |
| the same, 25,576 characters | "Too many line continuations" | the same, at load |
| `v = 1 +`, spaces, ` _` to 24 x 1,023 characters, then a line `1` | builds, 2 | |
| the same to 25 x 1,023 characters, then a line `1` | "Too many line continuations" | |

So a statement can't be longer than 25 pieces of 1,023 characters, however its lines are broken.

### Two long lines in one statement: the tail that vanishes

When one statement has more than one physical line over 1,023 characters, the result depends on its *first* line. In
the table, "long" is a line of more than 1,023 characters, and the last line's tail is what follows its 1,023rd
character:

| The statement's lines | Its last line's tail | Due if every character counts | `/make` |
|---|---|---|---|
| short, long | ` + 1000` | 1356 | **1356** |
| short, long, long | ` + 1000` | 1613 | **1613** |
| short, long, long | ` 1`, completing the sum | 515 | **515** |
| short, long, short | | 259 | **259** |
| long, short | | 300 | **300** |
| long, long | ` + 1000` | 1630 | **630, and no error** |
| long, short, long | ` + 1000` | 1631 | **631, and no error** |
| long, long | `Print #f, "tail ran"` | 630, plus a line saying `tail ran` | **630, and no `tail ran` line** |

- **With a short first line,** every long line is kept whole and read in pieces. A long first line followed only by
  short lines is kept whole too.
- **With a long first line,** each later long line loses everything after its 1,023rd character. The build reports
  no error, and the program gives the wrong value. A tail that would be a statement of its own didn't run either.
- **Two controls agree with this.** With a long first line, a second line whose cut leaves `... +` dangling is a
  Syntax error, as it would be with its tail gone. With a short first line, a second line whose tail is `v = v + 1000`
  is a Syntax error too, because that tail is kept and joined to the sum.

Two of these were run in the IDE, and it gave the same values: 630 for long, long, and 1356 for short, long.

### Long chains and deep nesting

The sweep first went 100, 250, 500, 1,000, 2,000, 3,000 and so on up to 6,000 terms, and 100 to 8,000 parentheses.
It was then bisected to the term. Every edge below is the same for native code and p-code. The IDE agreed
wherever it was tried: both edges of the first row, of the one-line row and of the parentheses, and `Debug.Print`
at 2,552:

| The statement | Builds at | Refused at | Continuations at the edge |
|---|---|---|---|
| `v = 1 + 1 + ...`, 250 terms to a line | **2,552** terms | 2,553 | 10 |
| `v = 1 * 1 * ...`, 250 terms to a line | 2,552 | 2,553 | 10 |
| `v = 1+1+1...`, no spaces, broken every 250 terms | 2,552 | 2,553 | 10 |
| `v = 1+1+1...`, no spaces, one physical line | **2,556** | 2,557 | 4 cuts, and 5 at 2,557 |
| `v = 1 + 1 + ...`, 120 terms to a line | | 2,552 | 21 |

| `Debug.Print 1 + 1 + ...`, 250 terms to a line | **2,551** | 2,552 | 10 |
| `v = a + a + ...`, `a` an `Integer` variable, 200 terms to a line | | 2,552 (not bisected) | 12 |

Every refusal was "Statement too complex". In the IDE it came at load, followed by the background-load box, and then

### Nested `If` blocks (2026-11-06, #3210)

**The question.** How deeply can `If` blocks nest? The probes above measured expressions only. Asked because
HexIDE's parse-depth guard refuses 58 nested `If` blocks, and the #1368 corpus has a 400-deep row.

**The obvious guess was a nesting limit for blocks, somewhere in the hundreds. P-code showed none.** It refuses the
procedure for its size, and at exactly the same point whether or not the blocks nest. Native code compiles far deeper,
until vb6.exe's own compiler overflows its stack.

**The probe.** The module above was used again, with these probe lines:
- **Nested:** n lines of `If True Then`, then `v = 7`, then n lines of `End If`.
- **The control:** the same lines unnested: n pairs of `If True Then` and `End If`, one after another, then `v = 7`.

| `If` blocks | Nested, p-code | The same lines unnested, p-code | Nested, native code |
|---|---|---|---|
| 100, 250, 400, 500, 1,000, 2,000 and 4,000 | builds, and runs to 7 | 4,000: builds | builds, and runs to 7 |
| 4,500 to 7,200, in steps of 50 to 500 | builds, and runs to 7 | builds, from 5,000 | builds, and runs to 7 |
| **7,227** | **builds**, and runs to 7; so does the IDE | **builds** | builds |
| **7,228** | **"Procedure too large"**; the IDE: "Compile error: Procedure too large" | **"Procedure too large"** | builds |
| 7,250 to 7,500, and 8,000 to 21,000 | "Procedure too large" | "Procedure too large", to 8,000 | builds, and runs to 7 |
| 22,000, 23,000, 24,000, 28,000 and 32,000 | "Procedure too large" | | **vb6.exe crashes**, with exit code 0xC00000FD, a stack overflow, and no message |

- **Every count from 7,201 to 7,249 was tried nested and unnested, as native code and as p-code.** In p-code, nested
  and unnested gave the same answer at every count, with the edge between 7,227 and 7,228.
- **This refusal is reported like a syntax error.** Unlike the two refusals above, `/make` names the file and the
  line, and adds "Build of '...' failed.".
- **In the IDE it came at Run, not at load.** There was a single box, with no background-load box after it.
- **The native crash looks like a depth problem.** The same 24,000 blocks unnested hadn't crashed when `/make` was
  stopped at its 90-second timeout. Its code generator, C2.EXE, was still running and was stopped by hand.

**The corpus's other two rows.** The two corpus shapes both built and ran, native and p-code:
- `v = ` with 400 pairs of parentheses around `1`, on one line of 805 characters, ran to 1;
- 400 nested `If` blocks ran to 7.

**What this shows.** In p-code, nested `If` blocks are limited by the size of their procedure, not by how deeply they
nest. Which measure of size it is, whether lines, statements or compiled bytes, wasn't measured, and nor were other
kinds of block: `For`, `Do`, `Select Case`, `With` and `ElseIf`.

### What the IDE shows

**A line over 1,023 characters appears in the code window broken in two.** The first line ends in ` _`, and End on
it puts the caret at Col 1024. The rest is on the next line. That is so whether or not the cut splits a token.

**Copying the module out of the code window doesn't give back what compiles.** With Ctrl+A and Ctrl+C, the first piece
comes out as 1,023 characters whose last two are ` _`. Those two overwrite two source characters, so `... + 1 + 1000`
came out as `... + 1 _` and then `0`. Yet the values show the characters are still there when the statement compiles:
the 1,024- and 1,025-character lines ran to 1254 and 256, and copied out they would be syntax errors. So treat the
values as the evidence, not the copy. Which of the two the IDE really holds wasn't settled. With a long first line,
the copy of a later long line ends at exactly 1,023 characters with no ` _`, and its tail doesn't appear at all.

**Saving refused.** In the 1,024-character case that builds, a line `Rem X` was typed in the code window and Ctrl+S
pressed. The IDE showed a box, "Line too long". The file on disk afterwards still had its 1,024-character line, and no
`Rem X` line.

### The rule, and the parts that resist one

**These hold for every case measured, in every build each was measured in:**

- A logical line may have at most **24 continuations**. A 25th is "Too many line continuations".
- **A physical line of more than 1,023 characters is read in 1,023-character pieces**, and each piece after the first
  counts as a continuation towards the 24.
  - A cut between tokens reads as if the line had been continued there.
  - A cut inside a number or a string literal splits it, which is a Syntax error.
- **"Statement too complex" refuses a statement that is too large.** That happens at about 2,550 terms of a chain, or
  7,644 nested parentheses.
- **Nothing is refused at run time.** No case raised Error 28 or any other error once it had compiled.
- **The IDE refuses at load.** It then loses the rest of the module and warns that saving would lose code.

**The tail that vanishes is measured but has no explanation here.** The cases are in the table above. Only the
first line's length was varied, so the rule is stated as narrowly as that. It gives a wrong value with no error, which
makes it the one result here that bites a program VB6 accepts.

**"Statement too complex" is not a count of terms, of tokens or of characters:**
- Spaces don't move it: doubling them, or removing them, left the edge where it was.
- Continuations do move it: 120 terms to a line fails where 250 to a line builds.
- So do the kind of term and the statement.

**A fit, not a rule I would defend.** Give each literal `1` a weight of 4, each operator 2, each pair of parentheses 2,
and each continuation 4, counting the 1,023-character cuts. Then every one of the 116 cases that assign a chain of the
literal `1`, or nested parentheses, to `v` is separated:
- every case that built totals 15,350 or less;
- every case refused totals 15,352 or more.

The fit was made from the spaced chains and the parentheses. It put the edge for the compact one-line chain at 2,556
or 2,557 terms before that was measured, and it measured 2,556. The 2,557-term line also crosses into a sixth piece,
so that prediction is weaker than it looks. The weights are fitted, not known. The variable, the two-digit literal and
`Debug.Print` sit outside the fit: each costs more than a literal `1` in an assignment, by amounts not measured.

### Not measured

- **Other statements:** an `If` condition, `Select Case`, a call's arguments, a module-level `Const`, `#If` and
  `#Const`. The corpus's rows use some of these.
- **Typing in the IDE,** as opposed to loading a file written outside it.
- **A long first line followed by a long line,** with the first line's length varied. Only 1,105 characters were tried.
- **Other limits,** such as procedure size, module size and the number of variables.
- **Double-byte text,** so whether the 1,023 counts characters or bytes. Every probe was ASCII.

### How it was driven

- A generator wrote each case's module and three projects.
- `/make` ran in the guest's session 0, with no window, and each exe was run with a timeout.
- The IDE runs went through the console-session agent described in [Reaching the VB6 *IDE*, not just the
  compiler](README.md#reaching-the-vb6-ide-not-just-the-compiler-2026-09-20). It launched `vb6.exe /run` and logged
  and dismissed every message box. The module was read with Ctrl+A and Ctrl+C after the code window was maximised.

Continuations elsewhere in the language are in [Line continuations and statement
separators](line-continuations-and-statement-separators.md#line-continuations-and-statement-separators-2026-09-02).

A rig note for the next person: **maximise the code window by its handle**, with `WM_SYSCOMMAND` and `SC_MAXIMIZE`,
not by clicking. With the same `.vbw` line, it opened in a different place here than for #3056, so that probe's click
coordinates would have landed on the toolbar.

### In HexIDE

HexIDE's interpreter reads a line far past 1,023 characters whole: #1930's tests run a 10,000-term chain written on
one line, and its depth guard raises 28. The deep-chain rows' expected 28 is therefore HexIDE's guard, not anything
VB6 does, since VB6 refuses each of those modules before it runs. What HexIDE should do past VB6's limits is #3203.
That issue also covers the risk that a line over 1,023 characters that HexIDE writes is read differently by VB6.

In the other direction, HexIDE's parse-depth guard refuses 291 nested parentheses and 58 nested `If` blocks. Both are
far inside what vb6.exe builds: that is #3210.
